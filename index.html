11/32

Routing

The description is the advertisement — what + when

  • State what it does AND when it applies.
  • Bad: "Helps with PDFs."
  • Good: "Extract text and tables from PDFs. Use when reading, converting, or inspecting PDFs."
  • ≤1024 chars — this is the routing menu the agent sees.

Taxonomy

Names + categories do the grouping

  • Domain prefix clusters a family:
  • tilelanggym-* · ascendc-* · triton-npu-* · dsl-* · ops-*
  • Category is the orthogonal cut:
  • regression · perf-analysis · doc-gen · ops-dev.
  • owner · origin · maturity drive the filters.

Layering

Load only what's needed, when it's needed

  • L1 description — always in context.
  • L2 SKILL.md body — on trigger (<5k words).
  • L3 references/ + scripts/ — on demand.
  • Scripts run outside the context window.
  • The entry stays thin and decisive.

These three decide whether the right skill is even found before it runs.

CAPTURE(ambient)CURATE(reviewable)HUB(shared)CONSUME(discovered)
Presenter notes

Speaker notes

USE is measurement; IMPROVE is the knowledge engine. This loop is the piece the landscape slide said the vendors still lack — and here the differentiator is the gate, not the capture.

Talk script

skill-foundry is two loops. The first is the boring, reliable one — USE. Run the regression, normalize the logs into a schema, render a report, and diff against a pinned baseline. Deterministic measurement, in thin scripts — not the agent's judgment.

The second is the interesting one — IMPROVE. When someone corrects the result, teach captures it; promote --pr turns it into a reviewed pull request that edits the skill itself. Next run, that failure is pre-annotated as known. The agent didn't get smarter — the harness did.

And the shape at the bottom — capture, curate, hub, consume — that loop is the product. Regression is just the first workflow bundled on top.

Background

USE is pure code (measurement); IMPROVE is code + review (judgment). The separation is the architectural claim — measurement is deterministic, knowledge is gated.

Presenter notes

Speaker notes

This is what 'keep it honest' means mechanically — capture auto, publication gated + reviewed + human-merged.

Talk script

If the system edits its own knowledge, how do you stop it silently corrupting it? Three buckets.

Green — automatic: running the scripts, capturing a correction. That's just appending. Safe.

Yellow — human, but rare: the triage judgment, merging the pull request, re-pinning the baseline when you deliberately decide the ground truth is stale.

Red — never: the system can never auto-remove or auto-change an existing check. Never.

Promotion runs mechanical gates — add-only, no-secrets, size, spec — and an LLM judge that must approve, then a PR a human merges. There's no escape hatch. Capture is automatic; publication is gated, reviewed, human-merged.

Background

this is the answer to the natural objection "won't it silently corrupt its own knowledge?" The SKILL_REVIEWER judge is the LLM; it's stub-able for demos (SKILL_REVIEWER='echo APPROVE').

Part 1 — Foundational concepts (from scratch)

1.1 What an "AI coding agent" actually does

An AI coding agent is a program (Claude Code, Codex, Cursor, Pi…) that takes your instruction, reads files, runs commands, and produces code/answers. It "reads" using a bounded working memory called a context window — a fixed-size budget of text (measured in tokens, roughly words/sub-words).

Two consequences follow:

  1. Context is a scarce resource. Everything you put in the window competes with the actual task. Waste it and the agent gets worse.
  2. The agent has no persistent memory by default. Each session it re-learns from whatever you hand it. That's the root of the whole talk.

1.2 Why "repeatable & shared" is hard

The same correction gets typed again and again — "use the right compiler," "that failure is known." Three bad homes for this knowledge:

  • One person's head — doesn't scale, leaves with the person.
  • A chat log — scrolls away, not searchable by the next agent.
  • A wiki — shared, but nobody reviews it, so it rots.

The industry's answer: put it in a file the agent reads on demand. That file, plus its conventions, is a "skill."

1.3 What a "skill" is, precisely

A skill = a folder (e.g. ascendc-env-check/) containing:

  • SKILL.md — the only required file. It starts with YAML frontmatter (metadata between --- lines): a name and a description, and optionally license, compatibility.
  • references/ — optional deep docs (guides, checklists, tables).
  • scripts/ — optional executable tools.

The two frontmatter rules that matter:

  • name ≤ 64 chars, kebab-case (my-skill-name), and must equal the folder name.
  • description ≤ 1024 chars, and must include trigger conditions — the words/situations that tell the agent when to load it. A skill with a bad description is dead: the agent never opens it.

Example description that triggers on the right moments:

Run pto-vmi CCE and DSL cases on the A6 simulator (dav_9201)…

1.4 Progressive disclosure (the load model)

Skills are lazy-loaded in three levels:

LevelWhen it's loadedSize guidanceWhy
------------
L1 metadata (name + description)always, into the agent's menu~100 wordstells the agent when to care
L2 SKILL.md bodyonly when triggered<5k wordsthe actual procedure
L3 references/ + scripts/only as neededunlimiteddeep knowledge; scripts run without entering the context window

The one-line principle you'll cite on stage: Anthropic says "the context window is a public good." Don't tax it with knowledge that isn't currently relevant.

1.5 The open Agent Skills standard

SKILL.md is now an open standard — the same folder works in Claude Code, Codex, Cursor, OpenCode, and Pi. That portability ("write once, run everywhere") is what the first section of the talk means by "the format is solved."

1.6 The always-on files (not skills, but neighbors)

Know the difference, because slide 4 shows them together:

Part 3 — skill-foundry (deep)

3.1 The idea in one sentence

Turn "run the regression" (and, in general, "do this repeated task") into skills + thin scripts + a pinned baseline, and make the skills improve themselves through a gated, human-merged loop.

3.2 The two loops (plus the product loop)

  • USE loop (run → report → review): thin scripts run suites, normalize logs (parse_gtest), render reports, and diff against a pinned baseline. This is deterministic measurement — code, not judgment.
  • IMPROVE loop (teach → promote --pr): a correction becomes a LRN-… entry, then a reviewed PR that edits the skill itself. This is knowledge — judgment, gated.
  • Product loop (the real point): capture → curate → hub → consume.

The famous line: after a correction is promoted and the same run is re-rendered and now shows the failure as "known" — "The agent didn't get smarter — the harness did."

3.3 The harness verbs (what each does)

./harness does only the skill-ops loop. The regression workflow is not a harness verb — it runs as thin scripts the skills reference.

The agent can auto-capture — when you correct it ("no / actually / remember…"), it logs the lesson and replies with the LRN-… id automatically.

3.4 The automation boundary (why the line is drawn where it is)

The governing question: "if the system edits its own knowledge, how do you stop it silently corrupting it?" The answer is a strict three-bucket boundary:

BucketWhatWhy it's safe/to-be-protected
---------

🟡 Human (rare)triage content (wrong→correct→action) · merge the PR · re-pin the baselinejudgment calls
🔴 Neverremove or change an existing checka wrong auto-edit ("that failure is now known") would hide real regressions

The key distinction: auto-append is safe (learnings/recent.md is the agent's own scratch memory); auto-edit is not (SKILL.md + known-failures.md are the team's shared source of truth).

Promotion therefore always runs: gates (learnings: add-only · no-secrets · size; new skills: spec incl. category/origin/owner · no-secrets) + an LLM judge (SKILL_REVIEWER) that must APPROVE — then --pr opens a PR a human merges after CI is green. "There is no escape hatch."

3.5 The six rules (full text + plain meaning)

  1. The pinned baseline is the ground truth. "Regression" means "diff vs reports/baseline/<target>.json." Re-pin only deliberately — a bad re-pin poisons every future run.
  2. Never auto-remove or auto-change an existing check. The harness only ever adds.
  3. p99 > +15% flags a perf regression even if average is stable. Averages hide tail latency — a small fraction of users seeing 3× latency is invisible in the mean.
  4. An npu-sim suite needs BOTH the CANN compile headers AND the simulator. run --list marks it ! if either is missing; python3 -m skill_foundry.lib.cann explains why.
  5. --all-suites auto-skips missing prereqs; an explicit --suite force-runs.
  6. Every run records context (git ref, dirty flag, host, env) in run.json — reproducibility, so a result can be rebuilt on another machine.

3.6 The MCP server (optional, typed)

The same loop is exposed as 5 typed tools — skills_list, skills_load, capture_skill, teach, promote — over HTTP/stdio (hosted at pto-b10.ddns.net/mcp). They call the same library in-process; the MCP server is transport, git is the source of truth.

3.7 Scale & targets

  • Targets: pto-isa (CPU simulator + NPU simulator ST for A5/A3/A6), pto-vmi (CCE/DSL + CA metrics), tilelangGym (SoftLib/ST compliance gates).
  • Baseline: pinned at reports/baseline/<target>.json; other reports/* are gitignored.

Two deterministic dav_9201 faults were 100% CANN's — and they were proven three independent ways before concluding that:

5.6 The THINK step, applied — the vshrs saga (find → think → capture)

FIND — a device compile fails with Cannot select: intrinsic %llvm.hivm.…. The intrinsic name exists but the target has no selection pattern. The a6-yellow-zone skill is already in context (its description triggers on "A6 / dav_9201") — but this wall isn't captured in it yet.

THINK — the agent asks four questions:

  1. Does the name even exist? — strings bisheng | grep -oE "llvm\\.hivm\\.vshr[a-z0-9_.]" | sort -u — lists declarations* across all arches (not what a specific target selects).
  2. What does the real IR ask for? — ptoas --emit-vpto-llvm-ir kernel.mlir -o /tmp/kernel.ll — get the exact operand/mask types.
  3. Which form actually selects? — sed the intrinsic name in the real kernel.ll to each candidate and re-run bisheng — seconds per candidate, and only the real IR reproduces the real selection context.
  4. Am I fooling myself? — keep the intrinsic's result USED; otherwise -O2 dead-code-eliminates the call and every candidate falsely looks "SELECTABLE."

Verdict — A6 selects the typed .z form; the winner for the bf16 broadcast selector was vshrs.v128u16u16.z.

CAPTURE — the agent writes the learning back: ./harness teach "vshrs 'Cannot select' → typed .z" → promote (gated + LLM-reviewed + human-merged) → the next run pre-annotates the failure as known.

Deeper lesson (worth saying explicitly): "Cannot select" is loud; "selects but wrong" is silent. vshrs errored honestly; vcgmax compiled fine and returned garbage. For numeric wrongness, the ground truth is the vendor's own CCE reference wrapper — __VF_VCG_V920 in …/tools/bisheng_compiler/lib/clang/*/include/__clang_cce_vector_intrinsics.h shows the exact A6 sequence = vcgmaxv2 + vpackv2.

5.7 The five-stage playbook (generalizes to any new dav_* chip)

  1. Discover the target — find the sim dir, list its lib/*.so; a lib/ with libruntime_camodel.so + model libs = runnable, only libruntime_camodel.so = incomplete (the Ascend920A trap).
  2. Compile headers — put the arch's headers first in the include path (-I $PTO_ISA_PATH before ${ASCEND_HOME_PATH}/include); arch_macro.hpp maps __NPU_ARCH__==<id> → the arch macro.
  3. Bring ptoas on board — accept the arch, emit the march, add converter/shift/reduction forms; probe the backend for every "Cannot select" and every numeric-wrongness.
  4. Diagnose camodel bugs — three-proof method; sidestep, don't fix.
  5. Dashboard per chip — own repo, themed web UI, arch badge, port (a6-vmi-dashboard → v200-vmi-dashboard), a kernels.txt source of truth, same build_dashboard.sh pipeline.

5.8 v200 / v926 (the "next chip" payoff)

  • v200 = v926, __NPU_ARCH__=9301; sim = davinci_model (build/exe/test_prj), not the CANN-tools camodel.
  • v926 is ISA-identical to A6 (dav-920r1) for VEC, so the A6 march is the bridge — compile with dav-920r1-vec; ptoas 0.69 accepts --pto-arch=v200/v926 as an A6 alias (no new emitters).
  • Arch string dav-926-vec/-cube (fallback dav-920r1-*); platform david_v200; CANN 9.2.0; MIX 1:1.
  • ISA deltas vs A6: vbitsort (TSORT32) absent, PIPE_MTE3 on CUBE absent, vshl/vshr MODE_ZEROING dropped, copy_matrix_cc_to_ub variadic.
  • The intrinsic-probe technique is unchanged because the ISA is the same — that's the "knowledge payed off twice" beat.

Part 8 — Hard questions & model answers

Q: "Isn't this just CI plus a wiki?"

CI runs tests and asserts pass/fail; it does not capture how to triage, what a failure means, or how to present it. This sits on top — it makes the response to a failure reusable and shared, with the same review discipline as code.

Q: "An AI editing its own knowledge — isn't that how it corrupts itself?"

Capture is append-only and automatic; editing shared skills is gated (add-only, no-secrets, size, spec) and LLM-reviewed, then merged by a human via PR. Never removes/changes an existing check. That's the automation boundary — the trust model.

Q: "Why not just put everything in one big CLAUDE.md / prompt?"

It's always in the context window and competes with the real task. Skills are lazy-loaded (progressive disclosure). Context is a public good — spend it only on what's relevant.

Q: "How do you stop facts drifting across many skills?"

Single-source / no reverse-dependency: one true source per fact, downstream consumes. Plus an index + machine gate — unindexed content doesn't exist for the agent, so orphaned duplicates can't silently persist.

Q: "Does the demo need the A6 simulator / special hardware?"

No. The demo uses a mock test runner with the real scripts — runs anywhere with python3 + git. The genuine A6 target runs on yellow (dav_9201).

Q: "What about the next chip?"

Same five-stage playbook. v200/v926 is ISA-identical to A6 for the vector unit, so the A6 march was the bridge and the probing technique carried over with no changes — that's the "knowledge pays off twice" proof.

Q: "Why sidestep the CANN bug instead of fixing it?"

It's a third-party binary; a source fix would be overwritten on upgrade, and the three independent proofs already show it's deterministic and not ours. The sidestep (teardown calls, SetDevice-first ordering) is stable and documented in the skill.
