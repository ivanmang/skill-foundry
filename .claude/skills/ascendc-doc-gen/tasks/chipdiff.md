# 芯片差异分析报告任务

## 任务目标

从 AscendC 头文件及关联代码中分析芯片/产品差异，产出一份全面的自然语言分析报告。
禁止臆测，所有结论必须有代码证据支撑；无法确认的内容标注"无法确认"。

**芯片→产品映射表**：
- 读取位置：`references/chip_mapping.md`

**昇腾950架构前置知识**：
- 技能启动时已读取 `references/ascend_950_npu_architecture.md`。本阶段仅用其理解架构术语，不得用作产品支持证据或芯片差异证据。

- 该段落是主要证据来源；若不存在，再按下方规则从代码自行分析

**代码上下文**：
- **【强制·首先读取】跨目录引用追踪产物**：`0_cross_dir.md` 必须已由 skill 前置预处理生成。本阶段只读取 `./outputs/{API名}/0_cross_dir.md`，不得在阶段内重复运行脚本。按报告中的"必读文件"、"产品支持证据线索"、"代码分析清单"和"验证清单"读取追踪到的外部头文件、对应实现文件和 api_check/kernel_check 文件；这些文件与 API 目录内文件同等分析。若 `0_cross_dir.md` 缺失或明显不完整，标记跨目录预处理未完成并停止本阶段，不得跳过追踪继续生成。
- **启动多个子任务并行探索**：将 `include/`、`impl/`、`examples/` 及追踪到的外部文件的分析任务分配给不同子任务同时执行，提高探索效率

- **【强制·逐成员分析】常规接口与对应同步接口合并为文档族时，分别检查每个成员的条件编译、产品支持、参数约束和调用链，再汇总共同点与有代码证据的差异。不得假定同步接口与常规接口完全相同，也不得把 `_s4`、`_sparse`、`_mx` 等非成员接口的差异带入。
- 主动探索代码目录结构，在 `include/` 对应 API 子目录（如 `adv_api/`、`basic_api/`、`c_api/`、`simt_api/` 等）、`impl/` 对应子目录（含 `detail/`、`tiling/`、`api_check/` 等）中搜索相关代码模式

## 芯片→产品映射表

**映射规则：**
- 代码中的芯片标识（如 `AddConfig("ascend910b", ...)`、`SocVersion::ASCEND910B`）对应映射表中的AI处理器类型，忽略大小写、空格和下划线差异进行匹配
- 映射表中带 `*` 号的行表示前缀匹配：只要代码标识以该前缀开头即可匹配（如 `ascend910b3` 匹配 `Ascend 910B*`）
- 精确匹配优先于前缀匹配（如 `ascend910` 精确匹配 `Ascend 910`，不会被 `910B*` 前缀捕获）
- 报告中严禁使用代码层面的芯片标识（如 ascend910b、ASCEND910_95、昇腾910_95），必须替换为映射表中的对外产品型号
- 违规示例（禁止）：`昇腾910_95 AI处理器`、`Ascend910B`、`ascend910_93`
- 正确示例：`Ascend 950PR/Ascend 950DT`、`Atlas A3训练系列产品/Atlas A3推理系列产品`
- 当代码中两个芯片标识共用同一实现，各自映射到对应产品型号即可

## 分析方法（3条规则，逐条执行，在所有源代码文件中查找）

**以下3条规则只用于收集产品支持候选证据，命中不等于最终支持。** 只有候选证据位于当前 API 的有效代码链路上，才能作为支持结论依据。有效代码链路包括：当前 API 的函数声明、函数体、wrapper/Impl/Cal 调用链、参数校验函数、底层 intrinsic/最终计算函数、tiling/host 校验调用链。与当前 API 无调用关系的同文件其它函数、其它重载、其它辅助接口中的命中，不得作为当前 API 支持证据。

**【强制】禁止间接推断产品支持**：只有代码中**显式出现**该芯片/架构标识时才能判定为支持。以下情况**不构成支持证据**：
- 代码分支行为与某已支持产品"一致"或"类似"
- 两个架构标识在同一 `if/else` 分支中合并处理
- 从产品系列归属推断（如"属于 A2 系列所以应该也支持"）
- 未在3条规则中命中任何显式芯片标识，或虽命中但无法证明命中代码位于当前 API 有效代码链路上的产品，产品支持结论必须判定为"不支持"，不得直接判为支持；其它非产品事实仍可标注"无法确认"

### 规则1：支持芯片提取

在所有源文件中查找 `AddConfig("芯片名", config)` 调用：
- 每个 `AddConfig` 代表一个支持芯片
- 汇总所有支持芯片，转换为对外产品型号
- 同时记录每个芯片对应的 config 变量名，用于后续差异分析

### 规则2：SoC 行为差异提取

在所有源文件中查找以下芯片条件分支：
- `SocVersion::XXX` 条件分支（如 `SocVersion::ASCEND910B`）
- `NpuArch::DAV_xxx` 条件分支（如 `NpuArch::DAV_3510`、`NpuArch::DAV_2201`）
- `GetCurrentPlatformInfo().GetCurNpuArch()` 相关判断
- 记录每个分支内的差异行为，包括但不限于：
  - tmp/workspace 大小计算路径差异
  - tiling 策略差异（分块大小、循环策略等）
  - 参数校验逻辑差异（不同芯片的 dtype/format/shape 校验条件不同）
  - 功能特性差异（某芯片支持某特性而其他不支持）
- 本规则既用于行为差异描述，也用于补充支持芯片/产品候选证据；命中后必须确认该分支属于当前 API 的有效代码链路，且没有 `NOT_SUPPORT`、空实现、恒 false 断言等否定证据，才能计入支持证据
- `NpuArch::DAV_xxx` 中的数值可通过映射表中的 `__NPU_ARCH__ 值映射` 转换为产品型号

### 规则3：编译期架构分支提取

在所有源文件中查找预处理分支：
- `#if (__NPU_ARCH__ == ...)`
- `#if (__CCE_AICORE__ == ...)`
- `#ifdef __DAV_xxx__`（如 `__DAV_C220_CUBE__`、`__DAV_C220_VEC__`）
- `IsRegBase(...)` / `isRegbase(...)` 接口调用
- 命中的架构标识只作为支持芯片/产品候选证据；必须确认该预处理分支属于当前 API 的声明、实现分发、校验或最终调用链，才能计入支持证据
- 若在当前 API 的有效代码链路上检测到 `IsRegBase(...)` 或 `isRegbase(...)` 接口调用，可作为 `Ascend 950PR/Ascend 950DT` 的候选证据；仍需结合该路径是否实际可达、是否存在否定实现综合判断
- 记录不同分支调用的实现函数差异（如 `*_regbase` 与 `*_arch32`）
- 分析不同实现路径的功能/性能差异（如果能从代码推断）

**【有效代码链路范围规则】** 通过 `#include` 引入的 check/impl 文件（如 `*_check.h`、`*_check_common.h`、公共 base impl 文件）内部可能包含多个 API、多个重载或多个辅助接口的架构分支。分析时必须遵守以下规则：

1. 先确认目标 API 的声明、wrapper/Impl/Cal、check、tiling/host 校验、底层 intrinsic/最终计算函数之间的有效调用链
2. 被 `#include` 引入的 check/impl 文件内部的架构分支，只有能被目标 API 调用链到达时，才能作为当前 API 的支持证据
3. 同文件中其它 API、其它重载、未被目标 API 调用的辅助函数里的架构分支，只能作为代码线索或其它 API 的证据，禁止计入当前 API 支持结论
4. 若候选支持路径最终进入 `ASCENDC_REPORT_NOT_SUPPORT`、`static_assert(false)`、恒 false 断言、空实现或仅报错分支，则该路径不能作为支持证据；需要在报告中记录为不支持或受限场景

### 代码片段提取方法

**收集匹配行**：按文件+规则分组记录匹配行。

**扩展到函数边界**：对于每个匹配行，找到包含它的最内层函数。向上找 `{` 确定函数开始，向下找配对的 `}` 确定函数结束。

**合并相邻区间**：如果相邻匹配区间间隔 ≤3 行，则合并。

## 报告要求（全面性）

**文档产品范围：** AscendC 文档固定使用以下 7 个产品项，报告中必须按顺序对每一项给出“支持”或“不支持”结论：
1. Ascend 950PR/Ascend 950DT
2. Atlas A3训练系列产品/Atlas A3推理系列产品
3. Atlas A2训练系列产品/Atlas A2推理系列产品
4. Atlas 200I/500 A2推理产品
5. Atlas推理系列产品AI Core
6. Atlas推理系列产品Vector Core
7. Atlas训练系列产品

**【强制】产品项白名单**：报告中的最终产品支持结论只能使用上述 7 个产品项。代码中的内部芯片标识和处理器型号可作为证据记录，但不得新增为产品项。310P 相关证据按 `references/chip_mapping.md` 的 AIC/AIV 规则分别判断 AI Core 和 Vector Core；不得再合并为“Atlas推理系列产品”。

报告必须覆盖以下所有维度，每个维度都要有明确结论（即使结论是"未检测到差异"）：

### 一、产品支持情况

- 按固定顺序列出 7 个产品项，并逐项给出“支持”或“不支持”结论，不使用“无法确认”、`TODO`、勾叉或其它占位状态
- 支持结论必须由候选证据 + 当前 API 有效代码链路共同证明；不得只因文件中出现芯片/架构标识就判定支持
- 未获得有效支持证据或存在否定实现/不可达路径时，结论写“不支持”，并说明原因
- 给出每个支持产品项的代码证据（文件路径 + 代码片段），证据必须能说明该产品对应路径位于当前 API 的声明、实现分发、校验或最终计算调用链上

### 二、数据类型差异

- 不同产品支持的数据类型（dtype）是否有差异
- 从 `\note support data type:` 注释中提取
- 从函数体内 `#if defined(__NPU_ARCH__)` 条件编译中的类型特化逻辑提取
- 如果不同芯片对应不同的 dtype 集合，逐产品列出

### 三、函数原型差异

- 不同函数原型支持的产品范围是否有差异
- 如带 `sharedTmpBuffer` 的重载与不带的重载是否支持不同产品
- 函数体内 `#if defined(__NPU_ARCH__)` 条件编译是否导致不同原型在不同芯片上可用
- 只按实际参数集合、模板参数、数据类型和产品支持差异描述原型。不得创造"精细控制版本"、"简化计数版本"、"Count版本"、"同步版本"等代码中不存在的分类名；可写"包含 `count` 参数的原型"、"包含 `repeat` 和 stride 参数的原型"

### 四、参数约束差异

- 不同产品的参数约束是否有差异
- 如对齐要求、shape 限制、取值范围是否因芯片而异
- 从 `kernel_check` 中的芯片条件分支提取
- 从 tiling 代码中的芯片条件分支提取

### 五、计算逻辑差异

- 不同产品的计算路径是否有差异
- 从实现代码中的 `#if defined(__NPU_ARCH__)` 条件编译提取
- 如不同芯片调用不同的内部实现函数
- 内部 CCE intrinsic、helper、`Impl`/`Cal`/`*_impl` 调用只能作为芯片差异证据，不得在结论中包装为用户可见功能、公式或模式名称

### 六、功能特性差异

- 某些功能/模式是否仅特定产品支持
- 如某个模板参数取值仅在特定芯片上有效

## 输出格式

输出纯文本报告，使用 Markdown 格式组织，按上述六个维度逐节输出。
每个维度必须包含：
1. 结论（一句话总结该维度是否存在差异）
2. 证据（引用具体文件路径和代码片段）
3. 详细描述（按产品组归并，描述相同的产品合并说明）

报告开头给出一段总体摘要（2-3句话概括芯片差异全貌）。
若某维度无差异或无法从代码确认，明确写"未检测到差异"或"无法从代码确认，需开发补充"。
