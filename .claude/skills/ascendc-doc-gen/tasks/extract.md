# AscendC 信息提取任务

## 任务目标

从 AscendC C++ 头文件及关联代码中提取全面的结构化信息，输出包含八大章节的报告：API 名称、产品支持情况、功能说明（含使用约束）、函数原型、参数列表（含结构体定义）、返回值、约束信息、调用示例来源（仅定位文件路径，不提取 Compute 函数内容）。
所有内容必须从代码中提取，禁止臆测。无法确认的内容按原因区分标注：
- `【待开发补齐】`：当前阶段缺少可读取证据、实现隐藏、脚本未覆盖、跨目录追踪不完整，或需要后续补抽取/补规则才能确认的文档必需信息。
- `【需开发确认】`：代码证据互相冲突、不同产品/路径行为不一致且无法从公开代码判断最终口径，或涉及接口 owner 语义裁定的内容。

### 代码目录结构与作用

AscendC API 的代码分布在多个目录中，各目录的作用和提取价值不同：

| 目录 | 作用 | 提取价值 |
|------|------|---------|
| `include/{api_type}/**/*.h` | API 接口头文件（函数声明、Doxygen 注释） | 基础语义、输入输出方向、模板默认值、显式约束、数据类型 |
| `include/{api_type}/**/*_utils.h`、`*_common.h` | 工具/公共头文件（结构体、字段定义） | 结构体字段默认值、字段含义、字段公式 |
| `include/{api_type}/**/*_tiling.h` + `impl/{api_type}/tiling/**/*.cpp` | Tiling 参数定义和校验 | 数值参数的单位、范围、合法组合、warning |
| `impl/{api_type}/detail/api_check/kernel_check/**` | Kernel 侧校验函数 | 单个参数和参数间的硬约束 |
| `impl/{api_type}/detail/**` | 实现代码 | 仅用于补证，不作为主来源 |
| `examples/` | 调用示例 | 调用示例代码 |

**注意**：
- 同一类 API 下，主 API 头文件和关联的 `*_utils.h`、`*_tiling.h` 需一并读取
- `impl/{api_type}/detail/` 只适合补证，不适合当主来源
- **跳过不读取**：所有 `.md` 文件、所有 `tests/` 目录下的文件
- 目录中 `{api_type}` 为 API 所属类别（如 `adv_api`、`basic_api`、`c_api`、`simt_api` 等）

### 3. 功能说明提取

从代码中提取功能说明所需的结构化信息，供 generate 阶段组织为最终文档。

**功能描述**（从代码提取）：
- 从 `\brief` 注释中提取功能描述原文
- 补充说明三点（如 `\brief` 未涵盖，从实现代码和参数注释推断）：API的功能（作用、目的）、使用后的效果、如何使用
- 记录 API 调用了哪些公开基础 API 或下游 wrapper（用于补充参数语义和约束证据）
- **公开/内部边界**：底层 CCE intrinsic、helper、`Impl`/`Cal`/`*_impl` 实现函数、寄存器/掩码设置函数和文件路径只能作为阶段证据，不能写成面向用户的功能语义、计算公式、使用场景或最终文档表述。若只能追到内部符号，记录"内部实现证据不足以形成用户语义"，并标注 `【待开发补齐】`
- `__inout_pipe__(...)`、`#pragma begin_pipe(...)` 等编译限定符/管线标记不得写入功能描述或自行翻译。只有源码明确给出公开流水类型，或已建立“公开 API -> 目标指令 -> ISA 流水类型”的完整映射时，才在提取报告中单独记录“流水类型证据”；不得从 intrinsic 名称、目录或模型常识推断

**功能场景识别**（从代码提取）：
- 识别不同的功能场景：仅在代码注释、条件编译、模板特化或明确分支说明存在真实行为差异时记录
- 函数重载本身不是功能场景。不得因为某个原型包含 `count`、`repeat`、`stride`、`sync` 等参数就创造"精细控制版本"、"简化计数版本"、"Count版本"、"同步版本"等代码中不存在的分类名
- 每个场景记录：适用条件、功能差异、涉及的芯片/产品范围

**计算公式**（有证据才提取）：
- 取消"所有 API 必须有公式"。只有代码注释、公开 wrapper 语义或可读实现明确给出数学/映射关系时才提取公式
- 计算类 API 可提取公式；数据搬运、配置、同步、包装、寄存器状态设置、格式转换等接口如果只有行为描述证据，可不输出公式，只记录行为说明
- 底层 CCE intrinsic/helper 调用、实现函数调用路径、寄存器设置函数调用不能改写成最终公式。例如 `intrinsic(dst, src, ...)` 只能作为内部实现证据，不能写成 `dst = intrinsic(...)`
- 对于调用公开基础 API 的 API：只能在该基础 API 的代码语义足够明确时提炼用户可见公式；若只能看到参数转发，标注 `【待开发补齐】`
- 公式变量名与函数原型中的变量名保持一致
- 公式后附加完整变量映射说明（如"其中，`src` 为输入 Tensor，`i` 为元素索引"）
- **公式符号闭包**：公式中出现的每一个符号都必须解释，包括函数参数、模板参数、结构体字段、临时辅助变量、下标变量、集合/范围变量、单位换算变量。禁止出现未解释的 `i`、`j`、`k`、`n`、`m`、`r`、`c` 等下标或循环变量
- **下标范围必须写明**：公式包含下标或循环索引时，必须给出每个索引的取值范围及其语义。例如块搬运/广播类公式中，`i` 应说明为块索引，取值范围 `0 <= i < blockCount`；`j` 应说明为块内 DataBlock 索引或元素索引，取值范围 `0 <= j < blockLen`
- **公式涉及的控制参数必须齐全**：影响计算范围、地址偏移、步长、重复次数、mask、axis、shape、block/gap/stride 的参数必须出现在公式或公式变量说明中。若无法说明控制参数与公式的关系，不输出公式，改为行为说明并标注缺失原因

**图示需求**（如适用）：
- 如 API 涉及数据排布、分块计算、地址映射等复杂逻辑，记录需要图示辅助说明的关键点

**输出格式**：

```
## 功能说明

### 功能描述
（API 做什么、使用后的效果、如何使用）

### 功能场景（如有多个）
#### 场景 1：xxx
...

### 计算公式
（可选项。仅在代码证据足够时给出数学表达式；证据不足时写"无可确认计算公式"，并说明缺少哪类代码证据）
```

### 4. 函数原型提取

**提取规则**：
- 从头文件中提取所有 `template <...> __aicore__ inline ...` 函数声明
- 保持与头文件中定义严格一致：函数名、参数名（含模板参数）、参数类型、返回值类型、函数限定符
- 原型数量与 `0_prototype.md` 严格保持一致，禁止遗漏
- `0_prototype.md` 已按 manifest 的 `memberApis` 生成成员并集。必须逐成员核对函数名和重载数；参数名序列只作为内部匹配键，用于将行为证据关联到具体原型，不得直接成为输出分组名称。不得自动并入 `_s4`、`_sparse`、`_mx` 等非成员接口。
- `## 函数原型` 必须保留 `0_prototype.md` 中的全部签名。`0_prototype.md` 只提供签名基准，不提供功能模式名称；必须结合公开注释、wrapper、实现分支、参数行为和校验逻辑识别用户可见的实际功能模式
- 对每个参数名序列建立“功能模式名称 -> 对应原型 -> 代码证据”映射。功能模式名称必须描述用户可感知的行为或使用场景，例如搬运组织方式、计算范围控制方式或数据处理方式，不能只复述参数是否存在
- 无法从代码确认功能模式名称时，明确记录“未确认公开功能模式名称”，只保留真实函数名和完整原型；不得把“原型1”“包含某参数的重载”“Count版本”等机械描述提升为功能模式名称
- 禁止使用“精细控制版本”“简化计数版本”“Count版本”“同步版本”“标准组合”“特殊组合”等模型自造分类；参数集合只能作为原型匹配键和证据，不能直接作为面向用户的分组名称
- **多个原型支持的硬件型号不一致时，必须分别标注每个原型支持的产品型号**
- **记录接口所在的头文件路径**

**输出格式**：

````
## 函数原型

- 头文件：xxx.h

### 原型语义分组

- 功能模式名称：{有代码证据的用户可见名称；无法确认时写“未确认公开功能模式名称”}
- 对应函数：{真实函数名}
- 对应参数名序列：{仅用于精确关联原型，不作为功能模式名称}
- 行为差异：{该模式的用户可感知行为}
- 代码证据：{公开注释、wrapper、实现分支、参数行为或校验逻辑}
- 声明：
  ```cpp
  template <typename T, bool isReuseSource = false>
  __aicore__ inline void Xxx(...);
  ```````

### 5. 参数信息提取

#### 参数取值的 4 类代码来源（按优先级）

参数取值和约束信息从以下 4 类代码中提取，优先级从高到低：

**来源 1：API 接口头文件** — `include/{api_type}/**/*.h`
- 提取内容：基础语义、输入输出方向、模板默认值、少量显式约束、枚举类型定义
- 来源：`\param` 注释、`\tparam` 注释、函数原型定义、`enum`/`enum class` 定义

**来源 2：工具/公共头文件** — `include/{api_type}/**/*_utils.h`、`*_common.h`
- 提取内容：结构体字段默认值、字段含义、字段公式、公共枚举类型定义
- 来源：结构体定义、`enum`/`enum class` 定义、内联函数、常量定义

**来源 3：Tiling 参数定义和校验** — `include/{api_type}/**/*_tiling.h` + `impl/{api_type}/tiling/**/*.cpp`
- 提取内容：数值参数的单位、范围、合法组合、warning、tiling API 使用的枚举类型定义
- 来源：tiling 参数结构体定义、`enum`/`enum class` 定义、tiling 校验代码中的 assert/warning/条件判断

**来源 4：Kernel 侧校验函数** — `impl/{api_type}/detail/api_check/kernel_check/**`
- 提取内容：单个参数和参数间的硬约束
- 来源：check 函数中的条件判断、assert、错误提示

**基础 API 架构实现文件（强制补充来源）** — `impl/basic_api/dav_*/kernel_operator_*_impl.h`、`impl/basic_api/kernel_operator_*_base_impl.h`
- 对基础 API，若 `0_cross_dir.md` 中包含 `impl/basic_api/kernel_operator_*_base_impl.h` 或 `impl/basic_api/dav_*/kernel_operator_*_impl.h`，必须读取这些文件；若调用链指向基础 API 实现但 `0_cross_dir.md` 未列出，标注跨目录追踪不完整，不得跳过架构实现文件直接给出结论
- 提取内容：按产品/架构分支的参数校验、数据类型组合、底层 intrinsic 实参、结构体字段是否实际使用
- 重点模式：`#if defined(__NPU_ARCH__)`、`ASCEND_IS_AIC`、`SupportType<Tuple<...>>`、`ASCENDC_DEBUG_ASSERT`、`ASCENDC_ASSERT`、底层 intrinsic 调用、`XxxImpl(...)`、`XxxCal(...)`
- 当架构实现文件中存在明确校验时，以该校验为当前产品组的强证据；找不到明确校验时，才允许结合底层调用参数传递关系分析；若仍缺少可读取证据，在 `2_extract.md` 标注"【待开发补齐】"，不得泛化为"【需开发确认】"

**如果 API 调用了基础 API，还需要从基础 API 的 check 代码中提取约束。**

#### 芯片差异信息提取方法

参数取值和约束在不同产品间可能存在差异。提取时必须识别并记录这些差异。

**差异信息来源（按优先级）**：

**来源 A：`1_chipdiff.md` 报告**
- 读取"二、数据类型差异"章节，获取不同产品支持的数据类型集合差异
- 读取"四、参数约束差异"章节，获取不同产品的对齐要求、shape 限制、取值范围差异
- 读取"六、功能特性差异"章节，获取特定模板参数取值仅在特定产品有效的信息
- 直接引用报告中的结论和代码证据，无需重复分析

**来源 B：代码中直接提取**
- `#if defined(__NPU_ARCH__) && (__NPU_ARCH__ == xxx)` 条件编译块内的数据类型特化逻辑
- 基础 API 架构实现文件中按产品分支出现的 `SupportType<Tuple<...>>`、`ASCENDC_DEBUG_ASSERT`、`ASCENDC_ASSERT`、底层 intrinsic 调用参数组合
- `\note support data type:` 注释中按芯片分段列出的数据类型
- `kernel_check` 代码中芯片条件分支内的校验逻辑差异
- `tiling` 校验代码中不同芯片的参数范围差异
- 使用 `references/chip_mapping.md` 将 `__NPU_ARCH__` 值转换为产品名称

**输出规则**：
- 参数取值在所有产品间无差异时，正常列出，不按产品拆分
- 参数取值区分产品时，按产品组分别列出（描述相同的产品合并），格式示例：
  ```
  - 支持的数据类型：
    - <term>产品A</term>、<term>产品B</term>：支持xxx
    - <term>产品C</term>：支持xxx
  ```
- 差异描述必须引用 `1_chipdiff.md` 中的具体章节作为来源

#### 逐参数提取维度

每个参数必须提取以下维度（如适用）：

1. **参数名**：与函数原型严格一致，不加粗
2. **输入/输出方向**：从 `[in]`/`[out]` 标记提取
3. **功能和场景**：从 `\param [in]/[out]` 注释中提取；复杂参数的使用场景从 `impl/{api_type}/detail/` 目录下的代码中分析
4. **数据类型**：
   - 从 `\note support data type:` 注释中提取，按位宽从小到大排列
   - **同一文件内不同 API 支持的数据类型可能不同，必须逐 API 提取，不可混用**
   - 原型中固定确定的数据类型不用单独说明
   - 数据类型存在多种情况的按规范名称列出，禁止使用 u8、s8 等不规范缩写
   - 接口支持的数据类型只和位宽有关时，用位宽表达：b8、b16、b32、b64
   - **按"芯片差异信息提取方法"提取不同产品的数据类型差异**
5. **TPosition 约束**：对 LocalTensor/GlobalTensor 类型参数，提取支持的 TPosition
6. **参数取值**：
   - 数值类参数：单位（数字和国际单位之间无空格，如"32字节"）、取值范围、默认值（从来源 1-3 提取）
   - C/C++整数类型只能证明参数的存储类型和可表示范围，不能证明接口合法取值范围。不得把`uint8_t`改写成接口范围`[0, 255]`；没有注释、校验、实现分支或ISA证据时，接口范围标注`【待开发补齐】`
   - 数据结构类参数：**完整结构体定义**（含各成员的类型、默认值、取值范围）、各成员介绍（从来源 2 提取）
   - 结构体定义过长时，给出所在头文件路径
   - 枚举类参数：当参数类型为 `enum`/`enum class`，或参数说明引用某个枚举类型时，必须追踪并提取该枚举类型的**完整定义**，包括枚举名、底层类型和全部枚举值；同时单独提取"当前接口支持取值"，二者不得混淆。完整枚举定义可以包含当前接口暂不支持的枚举值，当前支持取值必须来自注释、校验代码、tiling 约束或实现分支
   - 有特殊含义的取值不使用"魔鬼数字"，需解释取值含义
   - 对用于控制行为的参数或结构体成员，若代码只给出取值范围或注释为 "flag"、"mode"、"control"、"enable" 这类泛化描述，必须继续检索实现调用、校验代码、同名特性示例、README 和调用样例，提取每个取值的具体行为、典型配置方式、与其他 API/参数的配合关系和不适用场景
   - 对预留、内部使用或对外无需设置的参数/结构体成员，必须识别并记录"用户配置要求"。识别信号包括但不限于：名称或注释含 `reserved`、`reserve`、`rsv`、`resv`、`unused`、`pad`、`padding`、`internal`、`default/internal config`，字段仅参与位域填充/保留位，只有默认值且无 setter/构造参数入口，或实现中由接口内部覆盖设置
   - **预留参数调用链判定**：若参数由用户传入或作为模板参数暴露，但沿 wrapper、Impl/Cal、kernel_check/host_check、底层 intrinsic/最终计算函数追踪后，实际不参与计算、不参与分支选择、不参与校验约束、不影响临时空间/地址/shape/数据类型组合/输出布局，且没有用户必须配置的注释或样例，则可作为预留参数强证据。代码中出现 `(void)param`、`not effective`、`unused`、`reserved`、`not enabled currently` 等可作为强证据
   - **预留参数反向约束**：参数参与分支、模板特化、校验、地址计算、shape计算、临时空间计算、数据类型组合判断、输出布局或底层 intrinsic 实参时，不能判定为预留参数。不得仅凭有默认值、名称像 `config`/`reserve`、或结构体字段存在默认初始化就判定为预留参数
   - **场景差异处理**：同名参数在不同产品、算法模式、重载或代码路径中使用情况不同，必须按场景分别记录；若某些路径未使用、另一些路径使用，不得给出全局预留结论，需标注差异或"【需开发确认】"
   - 对上述参数/成员在 `2_extract.md` 中明确标注：`需要用户设置`、`用户无需设置，保持默认值`、`预留字段，保持默认值`、`接口内部使用，用户无需设置`、`【待开发补齐】` 或 `【需开发确认】`。保留代码证据，但不得仅因结构体中存在字段就推断为用户必须设置
   - **按"芯片差异信息提取方法"提取不同产品的参数取值差异**
   - 如单位在不同场景/数据类型下不同，需解释为什么是该单位以及不同数据类型下的换算关系
7. **参数配置方法**：复杂或有特殊要求的配置需提供说明
8. **参数间配合关系**：参数需要和其他参数或 API 配合使用时，描述配合关系
9. **约束条件**：单个参数的约束就近填写
10. **特殊值的处理**：特殊输入值的行为

**用户配置要求识别**：
- 函数签名中的参数必须保留；结构体成员也可保留，但每个参数/成员必须区分是否需要用户配置
- 对构造函数参数、setter 方法、调用样例中显式赋值的字段，优先判断为用户可配置字段；仍需结合注释和约束说明是否必须设置
- 对预留位、填充字段、内部编码字段、兼容旧名称字段、仅由实现内部赋值的字段，标注为预留/内部/无需设置，不把它们写成普通功能参数
- 对用户传入但底层未实际使用的参数，必须记录调用链证据。例如：外层接口接收该参数，但最终计算函数不接收或不消费该参数；实现中显式 `(void)param`；host/tiling 代码提示该参数 `not effective`。只有完成调用链追踪后才能标注为预留参数
- 如果参数只在 check 函数中作为模板参数出现，但 check 函数为空实现或未消费该参数，且最终计算不使用该参数，可记录为预留参数证据；如果 check 函数用该参数做约束校验，则不能判为预留
- 如果证据冲突，例如字段名称像预留字段但样例显式设置，必须在 `2_extract.md` 记录冲突并标注"【需开发确认】"

**无注释参数补全与代码内语义追踪**：
- 当接口声明缺少 Doxygen `\param` 注释，或注释未覆盖全部函数参数时，禁止省略未注释参数；必须沿调用链继续追踪 wrapper、Impl、Cal、check 函数、参数结构体和底层调用来补齐每个参数的语义、单位、范围和约束
- 重点追踪模式：`Xxx(...) -> XxxImpl(...) -> XxxCal(...) -> intrinsic(...)`、`CheckFuncXxx(...)` 构造的 `check::*ApiParams` 字段、`ASCENDC_CHECK_VALUE_RANGE`、`CheckValueRange`、`ASCENDC_ASSERT`、`SupportType`、`CheckTensorPos`、`CheckTensorAlign`
- 对于数据搬运、广播、矩阵搬运类接口，`blockCount`、`blockLen`、`srcGap`、`dstGap`、`srcStride`、`dstStride`、`repeatTimes`、`mask` 等控制参数必须逐项说明，不得因为头文件无注释而只写输入/输出 Tensor
- 对 `mode`、`pattern`、`flag`、`enable`、`disable`、`source`、`repeat`、`stride`、`gap`、`len`、`burst`、`count` 等控制参数，必须建立“目标参数 -> 下游实参位置 -> 下游参数名/结构体字段 -> 检查函数/范围检查/分支条件”的证据链
- 若目标参数只转发到内部 intrinsic，先使用 `0_semantic_links.json` 的候选，再按需进行**精确符号语义旁路追踪**：以同一 intrinsic/最终 callee 的完整符号名和同一实参位置检索公开基础 API、公开 wrapper、公开参数结构体、check 代码和实现分支。禁止按名称相似、同目录或同功能类别类比。
- `evidenceLevel=mapping_only` 只证明目标参数与关联公开参数沿代码传播到同一底层符号的同一实参位置；必须回读关联公开接口的声明、实现、校验或 ISA 映射，形成“目标形参 -> 实现传播 -> 同落点 -> 关联公开参数 -> 明确语义/约束”的闭环后，才能确认用户语义。
- `evidenceLevel=name_hint_only` 只用于定位可能相关的符号，不能证明参数含义、单位、合法范围、数据类型组合或逐值行为；不得直接写入提取结论。
- 关联公开接口只提供语义证据，不是当前文档成员。不得把其原型或独有形参并入当前 API 的函数原型/参数列表。若确认当前正式参数控制一个没有显式形参的语义操作数，必须将该操作数记录为“隐含语义操作数”，并绑定到控制它的正式参数及适用条件。
- 旁路追踪得到的语义只有在公开注释、公开结构体字段、显式检查或 ISA 映射中得到确认后才能写入结论；必须把读取文件加入 `## 代码分析清单`。内部符号只作为证据，不得出现在最终文档
- 控制参数的语义证据按以下强度判断：显式枚举/常量及注释、对该参数的分支或校验、与目标实参位置明确映射的 ISA 字段为强证据；仅有参数名、下游参数名、同族接口名或数值后缀为弱证据。弱证据只能作为继续追踪的线索，不能支撑“某某模式选择”“控制某某模式”这类看似完整的用户语义
- 测试若只用任意哨兵值验证实参原样传递，只能证明参数透传，不能证明该值合法，也不能证明取值范围、位宽编码或逐值行为。不得把这类测试值写入支持取值
- 同族接口、数字后缀接口或 `MODE1`/`MODE2` 一类常量，只有在代码注释、常量定义、相同最终 callee 的相同实参位置或明确 ISA 映射同时给出行为对应关系时，才能用于解释逐值语义。仅名称对应只能证明存在同族模式，不能推导模式行为
- 每个控制参数必须分别记录“可确认的公开功能”“支持取值”“每个取值的行为”“单位/编码位宽”“与其他参数的关系”。其中任一项缺少强证据时，只对该项标注 `【待开发补齐】`，不得用参数名直译或底层调用名填充缺项
- 若代码只能证明参数传递关系，不能证明具体取值含义或用户语义，必须标注 `【待开发补齐】`，不得把底层 intrinsic 名称、helper 名称或实现函数名包装成中文概念
- 若下游结构体字段或实现注释揭示了隐含语义操作数（如初始矩阵来源、bias table、缓存位置、mask 来源等），必须记录该字段与当前公开参数之间的映射；相关数据类型组合或参数组合约束必须包含这个语义维度，但最终文档优先使用公开参数名和用户可见概念表达
- 分形/数据排布/固定模式 bit pattern 等无法从 C/C++ 代码直接推出的内容，只能来自`0_isa_reference.md`中的明确ISA证据、代码注释或常量表；没有证据时标注 `【待开发补齐】`，不得根据TPosition、Buffer名称或模型常识补写
- 使用ISA证据时，必须先通过公开API到实现调用、目标指令名和参数位置建立映射，再引用对应指令的单位、范围或分形要求；仅名称相似或同属搬运/计算类别不能建立映射。`0_isa_reference.md`不存在或缺少该映射时保留`【待开发补齐】`

**多参数组合约束提取**：
- 当数据类型、TPosition、shape、取值或功能行为由多个参数共同决定时，必须作为"多参数组合约束"记录到 `## 约束信息`，不要拆散到单个参数后丢失组合关系
- 先从 `## 函数原型` 建立"实际参数集合清单"：每个重载/模板原型都记录完整参数名、模板参数到实参的映射、参数结构体类型，以及该原型适用产品组。后续所有跨参数约束都必须挂到其中一个或多个参数集合上
- 组合约束按实际函数原型的参与参数集合提取。约束涉及 N 个参数，输出就必须保留 N 个参数维度；不得只记录其中 N-1 个参数的组合，再用"某参数存在时也支持/不支持"等文字补充
- 当某个参数只存在于部分重载或部分原型中时，它不是特殊分类依据，只是对应参数集合中的普通参与参数。输出时必须为包含该参数的参数集合单独记录完整组合；不能把该原型压缩为另一个参数集合的附加说明
- 遇到 `SupportType<Tuple<...>>`、`static_assert`、`ASCENDC_DEBUG_ASSERT`、`ASCENDC_ASSERT`、check 函数、底层 intrinsic 分发或模板特化同时涉及多个参数时，必须逐项展开每个 Tuple/条件对应的实际参数名和值，不得只记录单参数类型集合
- 特殊数据类型、特殊格式、特殊功能分支必须列出每一个明确组合；禁止在提取报告中概括为"标准组合"、"特殊类型组合"、"支持与某原型相同组合"、"额外支持"或"同上"
- 不同产品组、不同函数原型、不同参数结构体或不同代码路径的组合关系不一致时，必须分别记录；路径无法覆盖时标注"【待开发补齐】"，证据冲突或需要接口 owner 裁定时标注"【需开发确认】"，不得用并集合并成一个全局结论

### 7. 约束信息提取

#### 约束来源 4 级优先级

**第一优先级：Kernel 侧校验函数** — `impl/{api_type}/detail/api_check/kernel_check/**`
- 最适合拿"必须满足"的硬约束
- 能拿到：
  - srcShape 各轴 > 0
  - `srcTensor.GetSize()` 下界约束
  - `dstTensor.GetSize()` 下界约束
  - TPosition 约束
  - `TensorReuseVerifyingParameters(...)` 地址复用/重叠约束
- **注意**：可能会有错/遗漏，需与其他来源交叉验证

**第二优先级：Tiling / Host 侧校验** — `impl/{api_type}/tiling/**/*.cpp`
- 能拿到：
  - 参数取值范围约束
  - 参数组合合法性
  - 某些参数"不生效"的 warning
  - tmp size 相关限制
- **【约束归属边界】** tiling 文件中往往同时包含目标 API 的 tiling 逻辑，以及 `GetXxxTmpSize`、`GetXxxTmpBufferFactorSize` 等辅助接口的实现。识别方法：头文件中有独立 `\brief` 注释的函数是独立文档 API。这类独立 API 在 `.cpp` 中的参数校验代码（`assert`/`CHECK`/条件判断）属于**该辅助接口自身的约束**，禁止归入目标 API 的约束说明。在目标 API 文档中，只需在相关参数描述里写明"需调用 `GetXxx` 接口获取所需空间大小"即可，不引入 `GetXxx` 本身的参数约束

**第三优先级：接口头文件注释和条件编译** — `include/{api_type}/**/*.h`
- 能拿到：
  - `support data type`
  - shape 维度匹配要求
  - 对齐要求
  - `ASCEND_IS_AIC`
  - `#pragma begin_pipe(V)`、`__inout_pipe__(V)` 等原始编译限定符/管线标记（只能作为代码事实记录，不得自行翻译为中文执行管线术语）
  - `__NPU_ARCH__`

**第四优先级：实现代码** — `impl/{api_type}/detail/**`
- 只适合补证，不适合当主来源
- 用来确认：
  - 某些约束是否真影响行为
  - 某些临时空间/公式约束是否来自真实实现

**地址对齐证据边界**
- 操作数地址对齐只能来自当前API的接口注释、kernel/host check、tiling校验、实现中的显式对齐计算、调用示例或`0_isa_reference.md`中的明确ISA要求
- TPosition和物理存储位置只说明数据所在位置，不能单独证明起始地址对齐值；不得根据“Global Memory”“L1 Buffer”等位置名称套用通用对齐表
- 未发现对齐校验不能推出“无对齐要求”。没有明确证据时标注`【待开发补齐】`；证据冲突时标注`【需开发确认】`
#### 约束考虑维度（带 ★ 为必查）

- ★ **源操作数与目的操作数地址复用约束**
  - 通过 kernel_check 代码中 `TensorReuseVerifyingParameters` 的调用传参判断
  - 查看传参：`VA_ARGS_TO_MAKE_TUPLE(dstTensor, srcTensor, sharedTmpBuffer)` 中的参数表示这些参数之间不能地址复用
  - `TensorReuseVerifyingParameters` 内部调用 `MultipleTensorReuseLoopCheck` 逐对检查参数地址重叠
  - 未出现在 `VA_ARGS_TO_MAKE_TUPLE` 中的参数不受此约束
- ★ **操作数地址对齐要求**
  - 优先从 kernel_check 中的 `CheckTensorAlign`、断言、错误提示等对齐校验提取
  - 其次从 `\param` / `\note` 注释中的对齐要求提取（如 `padded to 32B aligned up`）
  - 再从 tiling 校验或实现代码中对齐相关的计算逻辑推断
  - 上述来源均无明确结论时标注"【待开发补齐】"，不得由TPosition或物理存储位置推导对齐值，也不得把未发现校验写成"无对齐要求"
  - 若参数支持多个`TPosition`且存在明确对齐证据，分别列出每个`TPosition`对应的要求；证据冲突时标注"【需开发确认】"
- **多个参数组合使用或参数之间的约束**
  - 从 kernel_check 中多个参数同时参与校验的条件判断提取
  - 从 tiling 校验中参数组合合法性检查提取
  - 从基础 API 架构实现文件中的 `SupportType<Tuple<...>>`、`ASCENDC_DEBUG_ASSERT`、底层 intrinsic 分发提取数据类型组合、参数取值组合和功能模式组合
  - 输出时按产品组和实际函数原型参与参数集合记录，保留参数名与组合值，禁止只写"标准组合"、"同某原型组合"、"特殊类型组合"等概括结论
- **参数名与函数原型保持一致**
- **在参数配置方面，和通用的API参数介绍相比有没有额外需要注意的地方**
  - 通用参数（如 dstTensor、srcTensor 等）在大部分 API 中的含义一致，但当前 API 可能有特殊要求
  - 数据类型的判断方法：
    - C++ 模板重载：通过 `template <typename T>` 的实例化判断
    - C 枚举：通过枚举值判断
    - 模板特化：通过 `if constexpr (IsSameType<T, xxx>::value)` 判断不同类型的特殊处理
    - `enable_if` 约束：通过 `Std::enable_if<Std::is_same<PrimT<T>, U>::value>` 判断类型匹配关系
  - 结构体参数中各成员在不同场景下的含义差异
- **在API使用、参数配置、计算结果排布方面开发者容易理解错误、易混淆的地方**
- **调用后是否需要恢复环境**
  - 需分析寄存器相关的代码，如 `set_mask_count()` / `set_mask_norm()` / `set_vector_mask()` 的成对调用
  - 数据相关：查看函数是否修改了全局状态（如 mask 寄存器、向量寄存器）
  - 只有当调用前后状态会影响用户后续代码、且需要用户显式配合或恢复时，才记录为最终约束；接口内部成对调用的 helper 只作为内部实现证据，不写入最终用户文档
- **代码限定符与管线标记**
  - `__inout_pipe__(V)`、`__inout_pipe__(MTE2)`、`__inout_pipe__(MTE3)`、`__inout_pipe__(S)`、`__inout_pipe__(FIX)`、`#pragma begin_pipe(V)` 等只能按代码原文记录
  - 禁止将上述标记自行翻译或扩写为"Vector管线"、"Vector流水线"、"Vector Core管线"、"Vector Core流水线"、"MTE管线"、"MTE流水线"、"Scalar管线"、"Fixpipe管线"等术语
  - 若术语表未给出某个代码标记的规范中文名，禁止创造中文译名；保留代码标记原文并说明"接口原型包含..."即可
  - 这类代码标记不应进入功能描述；只有当它构成用户可见的使用约束时，才在"约束信息"中原样记录
- **API 对特殊数据类型（如 int4b_t）的支持差异**
- **API接口支持的开发方式有无约束**（Kernel 直调开发方式和工程化开发方式是否都支持）
- **其他从代码中提取到的、开发者使用时需要了解的约束**

（注意，接口的约束要全面，保证资料内容完备性）

#### 输出参数初始化需求（构造调用示例前置证据）

对所有输出参数（如 `dstTensor`、`dst`、`yLocal`、`outTensor`）必须额外分析实现代码，判断调用前是否需要用户初始化或清零，并在"约束信息"中记录明确结论和来源：

- **不需要初始化/清零**：实现代码对输出参数执行覆盖写入，例如 `DataCopy(dst, ...)`、`Cast(dst, ...)`、`Adds(dst, src, 0, ...)`、`BlockReduce*`/`WholeReduce*`直接写入输出、`Reg::StoreAlign(dstAddr, ...)`、`Reg::StoreUnAlign(... dstAddr ...)` 等，且未读取输出参数原值参与计算。
- **需要初始化/清零**：实现代码读取输出参数原值参与累加、归约或原地更新，例如 `Add(dst, dst, ...)`、`Muls(dst, dst, ...)`、`RepeatReduceSum` 累加模式、`AtomicAdd`、对 Global Memory 输出地址做累加写回，或代码/示例/注释明确要求先清零。
- **无法确认**：未能从实现代码确认输出参数是否覆盖写入或依赖旧值时，缺少可读取证据标注"【待开发补齐】"，证据冲突或需接口 owner 裁定时标注"【需开发确认】"，禁止在调用示例中自行加入清零操作。

记录格式：

```
### 输出参数初始化需求

- dstTensor：不需要调用前清零。来源：xxx_impl.h:xx `Cast(dstTensor, ...)` 覆盖写入；未发现读取 dstTensor 原值参与计算。
```

### 8. 调用示例提取

#### 定位规则

所有调用示例位于 `examples/` 目录下，根据 API 所属类别确定子目录：

| API 所在目录 | 示例所在目录 |

在对应子目录下按 API 名称（全小写）递归搜索目录名和 `.asc` 文件，找到包含目标 API 调用的示例文件。

#### 提取规则

1. **定位示例文件**：在 `examples/` 对应子目录中按 API 名称递归搜索，优先选择目录名或文件名与 API 名称精确匹配的 `.asc` 文件；若无精确匹配，再选择文件内容包含目标 API 调用（如 `AscendC::API名`、`API名<`、`API名(`）的 `.asc` 文件
