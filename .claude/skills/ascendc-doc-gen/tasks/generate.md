# AscendC 文档生成任务

## 任务目标

汇总 chipdiff 和 extract 阶段产出，生成完整的 AscendC API 参考文档。文档章节固定，产品支持情况使用固定注释列表，其余表格统一使用简洁 Markdown 表格。

**核心要求**：
1. **API 名称**：使用 extract 报告中的 API 名称（大驼峰形式），在整个文档中保持一致
2. **信息来源**：所有内容必须从阶段产出报告（`1_chipdiff.md`、`2_extract.md`）中获取，禁止臆测。本任务描述中的示例仅说明格式，不要照搬
3. **前后自洽**：功能说明、参数说明、约束说明之间不能出现前后矛盾；若没有可确认公式，不要为了自洽而臆造公式
4. **公开/内部边界**：最终文档只能出现目标公开 API、公开类型、公开宏和用户可感知行为。底层 CCE intrinsic、helper、`Impl`/`Cal`/`*_impl` 实现函数、寄存器/掩码内部设置函数和代码路径默认禁止进入正文、公式、参数说明和约束说明
- **【强制·文档 identity】**读取 `0_preprocess_manifest.json` 的 `documentApiName`、`memberApis` 和 `callingConvention`。最终文档标题使用 `documentApiName`，函数原型和参数差异覆盖全部 `memberApis`；调用示例至少覆盖 `document-root` 与 `sync-counterpart`，`source-document-group` 变体可按功能模式选取代表性调用。不得混入成员闭集外接口或其它调用约定。
5. **严禁输出思考过程**：输出必须是纯净的文档正文，严格按模板章节结构输出。禁止出现以下内容：
   - 分析推理过程（如"根据代码中的宏定义判断..."、"结合芯片映射关系..."）
   - 自我纠正或注解（如"注意：此处..."、"正确示例为..."）
   - 判断依据说明（如"由于函数体内含xxx判断，表明..."）
   - 推测性描述（如"若存在"、"需确认是否支持"）
   - 章节间的过渡/总结性段落
   只输出面向最终读者的技术文档内容，不输出任何中间思考、分析或推导文字

## 输入输出约定

### 输入

- `./outputs/{API名}/1_chipdiff.md` — 芯片差异分析报告
- `./outputs/{API名}/2_extract.md` — 信息提取报告（主要信息来源）
- `./outputs/{API名}/0_prototype.md` — 外部预处理提取的函数原型，作为函数原型章节的优先来源
- `./outputs/{API名}/0_preprocess_manifest.json` — 文档 identity，包含规范文档名、文档成员、调用约定和源文件范围
- `./outputs/{API名}/0_semantic_links.json` — 跨公开包装接口参数传播候选；只用于核对 `2_extract.md` 的闭环结论，不得直接生成语义
- `./outputs/{API名}/0_call_example.md` — 外部预处理调用示例结果；generate 阶段仍需生成模型 fallback 示例，最终合成时脚本有效示例会替换该章节
- `references/chip_mapping.md` — 芯片→产品映射表
- `references/common_terminology.yml` — 术语规范
- `references/ascend_950_npu_architecture.md` — 昇腾950架构前置知识；技能启动时已读取，用于术语和架构表述约束，不作为 API 事实来源

当阶段产出信息不足时，可主动探索 `include/`、`impl/` 对应目录补充分析。**补充分析时只能读取外部预处理生成的 `./outputs/{API名}/0_cross_dir.md`，不得在 generate 阶段运行 `scripts/extract-cross-dir.js`。若 `0_cross_dir.md` 缺失或明显不完整，停止补充分析并标注"【待开发补齐】"，不得跳过跨目录追踪自行补写结论。**

不确定信息标记口径：
- `【待开发补齐】`：缺少可读取证据、实现隐藏、脚本未覆盖、跨目录追踪不完整，或需要后续补抽取/补规则才能确认的文档必需信息。
- `【需开发确认】`：代码证据冲突、不同产品/路径行为不一致且无法从公开代码判断最终口径，或涉及接口 owner 语义裁定的内容。

### 输出

- `./outputs/{API名}/3_generate.md`

## 功能说明

> 说明：本任务描述中的"示例"仅用于说明结构与写法，不是事实来源。生成时禁止复用示例里的 API 名称、参数名、数值、产品名与场景，必须以阶段产出报告为唯一依据。

### 输出格式模板

功能说明的输出结构如下（每个部分的具体写作要求见后文）：

```
## 功能说明

{功能描述段落}

{如 2_extract.md 给出可确认公式，再输出计算公式；没有可确认公式时，不输出公式块。}
```

**多功能场景时**，在 `## 功能说明` 下按场景分段说明：

```
## 功能说明

- **{场景名称}**：{功能描述段落}
  {如该场景有可确认公式，公式块和变量说明缩进在同一列表项内；没有可确认公式时，不输出公式块。}

- **{场景名称}**：{功能描述段落}
...
```
### 各部分写作要求

#### 功能描述
- 以 `2_extract.md` 中"功能描述"章节的内容为基础，组织为面向读者的文档语言
- 明确说明三点：**API的功能（作用、目的）是什么？使用后用户体验的变化？如何使用？**
- 简洁精炼，用一两句话直接说明API做什么，不要添加与API功能无直接关系的背景描述
- 采用规格说明式语言，每句话都传递关键技术信息，不要有解释性铺垫或过渡段落
- **参数名引用时必须给出含义**：功能描述正文中若引用参数名称（包括：函数模板参数如 `T`、`accType`；结构体字段如 `outter`、`inner`、`n`；函数参数名），**必须在首次引用时同步说明其含义**（例如："输入数据类型`T`"、"行数`outter`"、"列数`inner`"），不可裸用参数名而不解释其语义
- **代码限定符不进功能描述**：`__inout_pipe__(...)`、`#pragma begin_pipe(...)` 等编译限定符/管线标记不得写入功能描述，也不得转写为"Vector管线"、"Vector流水线"、"MTE管线"等自然语言执行管线描述；即使 `2_extract.md` 的功能描述中包含这类表述，生成时也必须删除

#### 计算公式
- **可选项**。只有 `2_extract.md` 明确给出可确认公式，且公式不是由底层 intrinsic/helper 调用改写而来时，才输出公式块
- 若 `2_extract.md` 写明"无可确认计算公式"、`【待开发补齐】`、只给出内部调用路径，或公式形如 `dst = intrinsic(...)`、`xxx = vreducev2(...)`，生成阶段必须删除公式块，改用功能行为描述
- 公式变量名与函数原型中的变量名保持一致，数学表达式复用数学符号保证简洁
- 公式后必须附加完整变量映射说明，覆盖公式中的全部符号
- **公式符号不能悬空**：公式中出现的所有函数参数、模板参数、结构体字段、下标变量、辅助变量、集合/范围变量和单位换算变量都必须在"其中，..."说明中解释。禁止出现未解释的 `i`、`j`、`k`、`n`、`m`、`r`、`c` 等符号
- **下标范围必须呈现**：公式使用索引时，必须写明索引语义和取值范围。例如块搬运/广播类公式必须说明 `i` 为块索引，`0 <= i < blockCount`；`j` 为块内索引，`0 <= j < blockLen`
- **控制参数不强行入公式**：`blockCount`、`blockLen`、`srcGap`、`dstGap`、`srcStride`、`dstStride`、`repeatTimes`、`mask`、`axis`、`shape` 等控制参数若不直接改变数值计算，只在参数说明或约束说明中描述其控制的范围、地址偏移或布局含义，不得为覆盖参数而伪造公式
- 如 `2_extract.md` 中标注了需要图示辅助说明的关键点，需在功能说明中增加图示说明
- **公式必须使用块级格式**，`$$` 必须单独占一行，公式内容在中间行。禁止将 `$$` 和公式写在同一行
- 多场景功能说明使用无序列表时，属于某个场景的"计算公式如下："、`$$` 公式块和"其中，..."变量说明必须缩进到同一个列表项内（通常为两个空格），不得顶格写成脱离该场景的独立段落

### 通用规则

**场景拆分**：
- 不同芯片版本支持的API功能不同时，在 `## 功能说明` 下按场景分段说明，不新增 `### 场景N`、`#### 场景N` 或以变体名命名的 Markdown 子标题
- 同一芯片版本支持的API功能不同时，使用短段落或无序列表分点说明；场景名称使用加粗短语（如 `- **{场景名称}**：...`），不使用标题层级
- 场景编号只在确有必要区分流程时出现在正文中，不作为标题层级

**禁止事项**：
- 不体现API内部实现原理，强调"做什么"而非"怎么做"
- 不介绍迭代的并行度PAR，公式中避免出现PAR
- 可选输入不在功能说明中体现，在参数说明中说明即可
- 参数配置逻辑放在参数说明中，不在此体现
- shape描述用英文括号，如 \(64, 64\)
- 同一章节内相同的概念名称、参数名、单位保持一致
- **禁止在功能说明中出现"使用约束"子章节或约束列表**，所有约束统一放在 `## 约束说明` 章节
- 禁止把代码中的 `V`、`MTE2`、`MTE3`、`S`、`FIX` 等限定符自行展开或翻译为未在术语表中定义的中文术语；需要保留时只写代码原文，例如"`__inout_pipe__(V)`"
- 禁止在正文、参数说明、约束说明、公式和示例注释中暴露内部 CCE 指令、底层 intrinsic、helper、实现函数和文件路径；包括但不限于 `vreducev2`、`vcopy`、`set_mask_count`、`asc_set_mask_count_begin`、`asc_set_mask_count_end`、`asc_sync_post_process`、`*Impl`、`*Cal`、`*_impl.h`

## 函数原型

### 结构组织要求
- `## 函数原型` 下禁止使用 `###`、`####` 等子标题。按 manifest 顺序用普通列表项组织。优先使用 `2_extract.md` 中具有代码证据的用户可见功能模式名称；禁止把“包含某参数的重载”“原型1”或参数集合改写成模式名称。
- “常规接口”“同步接口”只表示 manifest 已确认的公开成员角色，不得改写成“标准版本”“同步版本”等模型自造版本名。同步行为差异只有在 `2_extract.md` 有代码证据时才说明。
- 一个 API 有多个函数原型时，先按真实函数名隔离，再按 `2_extract.md` 已确认的用户可见功能模式或产品组分组。每个模式必须能回溯到 `2_extract.md` 的原型语义分组及代码证据。
- 每个分组使用一个无序列表标签，标签后紧跟一个 C++ 代码块；同组的全部重载完整放在该代码块中，不为每个重载创建 `###` 标题
- 同一代码块可包含同一真实函数名下的多个完整重载。`2_extract.md` 已确认不同功能模式时，按模式拆分代码块；未确认公开功能模式名称时，只按真实函数名建立一个中性列表项并完整列出其全部重载，不再按参数名机械命名分组
- 参数名序列不同但没有公开功能模式名称时，列表标签只写真实函数名，不添加“包含某参数的重载”“原型1”等机械标签。参数差异由代码块中的完整声明体现。
- 功能模式名称必须有公开代码注释、公开 wrapper、实现条件分支、参数行为或校验逻辑证据。证据不足时不得命名模式，只按真实函数名组织完整原型。
- 后续内容中要区分不同原型的，与函数原型中的分组顺序保持相同

### 内容要求
- **一致性**：函数原型签名集合必须与 `0_prototype.md` 完全一致。允许把同组的多个声明合并到一个代码块，但每个声明都必须完整保留；若 `0_prototype.md` 与 `2_extract.md` 不一致，以 `0_prototype.md` 为函数签名文本来源
- **禁止代表性压缩**：不得只展示某个数据类型的代表原型，再用“其余类型相同”“同样包含”“以T为例”等文字代替其它重载
- 使用 C++ 代码块呈现。每个函数声明独占一个物理行并保留末尾分号，与 `0_prototype.md` 文本一致；模板声明行单独保留在对应函数声明前。禁止把一个函数声明手工折成多行参数列表。
- 原型标签只使用真实函数名，以及 `2_extract.md` 已确认且有代码证据的用户可见功能模式或产品范围。参数名、参数集合和原型序号不能充当模式名称；不得创造“精细控制版本”“简化计数版本”“Count版本”“同步版本”等分类名。
- 只有 `2_extract.md` 明确给出使用方式或临时空间管理差异时，才在代码块后补充说明；否则只写中性事实
- 若多个原型仅由 `LocalTensor`/`GlobalTensor` 参数类型区分数据来源或目的位置，不得把 Tensor 类型拼成搬运方向；只有 `2_extract.md` 给出 TPosition 时才写真实数据通路
- 不输出接口所在头文件、代码文件路径或证据来源说明
- 多个原型支持的硬件型号不一致时，在对应分组后写明不支持该组原型的产品；标签中已包含产品范围时，不重复产品名

**格式示例（仅示意结构，模式名和函数签名必须以报告为准）：**

- TargetApi，{经 `2_extract.md` 代码证据确认的用户可见功能模式名称}：
  ```cpp
  __aicore__ inline void TargetApi(...);
  ```

没有可确认功能模式名称时：

- TargetApi：
  ```cpp
  __aicore__ inline void TargetApi(...);
  __aicore__ inline void TargetApi(...);
  ```

## 参数说明

参数表按实际函数原型组织：
- 当所有原型均没有模板参数和函数参数时，不生成表格，`## 参数说明`章节正文只输出单独一行“无”，不得加句号、列表标记或附加说明。
- 没有模板参数且各重载中同名参数语义一致时，只写一个接口参数说明表。
- 有模板参数时，先写模板参数说明表，再写接口参数说明表。
- `2_extract.md` 明确确认不同功能模式或参数集合，且同名参数的语义、单位、范围或约束不同时，允许使用 `### {功能模式}参数` 子标题，并为每个模式分别建立 Markdown 参数表。
- 模式名称必须来自 `2_extract.md` 中公开代码证据形成的闭环结论。证据不足时不得创建模式子标题；按真实函数名建立参数表，并通过适用原型说明精确关联参数差异。
- 每个表必须覆盖对应原型组的全部参数；同名参数在不同模式含义不同时不得合并成一行。
- 结构体成员说明使用规范表题和 Markdown 表格，不新增“结构体成员说明”等泛化子标题。
- **参数说明必须完备，禁止遗漏任何参数。**
- **正式形参闭集**：参数表行必须与 `0_prototype.md` 的模板参数和函数形参对应。关联公开接口中的独有参数或隐含语义操作数不得伪造成当前接口参数行。
- **隐含语义操作数表达**：`2_extract.md` 已确认某个正式参数选择或控制隐含语义操作数时，在该正式参数或相关输出参数的描述中写清适用条件、来源或位置、行为和已确认的数据类型；未知项逐项保留待补齐。不得仅写关联实现名，也不得新增不存在的形参。
- 参数取值范围以 `2_extract.md` 中提取的明确信息为准。
- 接口声明中的每个参数都必须在对应参数表中出现；证据不足时保留“【待开发补齐】”或“【需开发确认】”。
- 所有表格必须使用简洁 Markdown 表格，禁止输出 `<table>`、`<thead>`、`<tbody>`、`<tr>`、`<th>`、`<td>`。
- 表格单元格内禁止使用 LaTeX 数学语法，范围统一写纯文本，如“取值范围：[1, 65535]。”。

### 参数描述书写规则

**参数名**：与函数原型严格一致，不加粗

**输入/输出**：输入表示入参，输出表示出参

**最小语义优先**：
- 对 `repeat`、`count`、`size`、`mask`、`src/dst stride`、`src/dst gap`、`burst/len` 等通用控制参数，若 `2_extract.md` 只确认参数名、类型、单位或简单含义，参数描述保持简短，不扩写内部执行机制
- 不得写“仅在精细控制版本中使用”“仅在简化计数版本中使用”“用于Count版本”等自造分类。只需写参数本身的语义；确需限定适用原型时，引用对应函数原型或 `2_extract.md` 已确认的功能模式名称。
- 示例：`repeat` 只需写`迭代次数。`，除非 `2_extract.md` 给出明确范围、单位或特殊值行为
**控制参数证据边界**：
- `2_extract.md` 若只记录了参数名、下游实参位置或透传关系，不得把参数名直译成完整语义。禁止把“Padding模式选择”“归约模式控制参数”“功能标志”等泛化短语作为参数的全部功能说明
- 只有 `2_extract.md` 提供显式枚举/常量及注释、分支/校验或明确 ISA 字段映射时，才能写支持取值、编码位宽和逐值行为。测试中的任意透传哨兵值不得作为合法取值
- 能确认参数所属的用户可见功能、但不能确认取值编码时，使用“用于配置{已确认的公开功能}。”这类有限表述，并在同一单元格中使用 `<br>` 分行写“支持的取值及各取值对应的行为【待开发补齐】。”不能确认所属功能时，不根据参数名补写功能，只保留待补齐项
- 最终文档不得出现“无法从公开代码确认”“实现仅透传”“代码未给出”“未发现校验”等证据过程话术。统一改写为面向读者的缺项，例如“取值范围【待开发补齐】。”、“各取值对应的行为【待开发补齐】。”

**参数术语**：
- 描述 `src`、`dst`、`srcGap`、`dstGap`、`srcStride`、`dstStride` 等参数时，统一使用"源操作数"和"目的操作数"
- 禁止引入"源端"、"目的端"、"源端地址"、"目的端地址"、"源端块间隔"、"目的端块间隔"等非规范名词；应分别改为"源操作数"、"目的操作数"、"源操作数地址"、"目的操作数地址"、"源操作数块间隔"、"目的操作数块间隔"
- 参数名和单位必须以函数原型、`2_extract.md` 和代码注释为准，不得改写或造词。禁止出现 `brust`；`n_burst` 表示连续传输数据块个数，`len_burst`、`src_gap`、`dst_gap` 等若 `2_extract.md` 明确单位为 DataBlock，则统一写`单位为DataBlock（32字节）。`

**存储位置表述**：
- 描述 AscendC 存储位置时，必须区分三层概念：`LocalTensor`/`GlobalTensor` 是 Tensor 类型，`TPosition` 是逻辑位置，`L1 Buffer`/`L0A Buffer`/`L0B Buffer`/`L0C Buffer`/`Global Memory` 是物理存储或内存空间
- 参数说明优先采用人工文档句式：`类型为LocalTensor，支持的TPosition为A2/B2。`、`类型为GlobalTensor。`。不要在参数表中把 `LocalTensor`/`GlobalTensor` 和物理 Buffer 写成括号同位语
- 功能说明和数据流描述优先使用逻辑位置。数据搬运类 API 通常描述为"搬运"，例如：`Load2D支持如下数据通路的搬运：`、`支持如下数据通路：A1->A2、B1->B2。`；矩阵计算类 API 可写为：`矩阵A、矩阵B和结果矩阵分别为A2/B2/CO1中的数据。`
- 搬运方向、功能场景和原型标签不得用 `Local→Local`、`GM→Local`、`Global→Local`、`Local->Local` 等由 Tensor 类型拼接出的模型自造标签代替真实数据通路；若只能从原型确认 Tensor 类型，应表述为"`src`为LocalTensor"或"`src`为GlobalTensor"，不能推断具体 TPosition。只有 `2_extract.md` 明确给出 TPosition 时，才写"A1->A2、B1->B2"、"GM->A1、GM->B1"等数据通路
- 物理 Buffer 只在必要场景出现：映射解释（如 `TPosition为A2时，对应L0A Buffer`）、地址对齐（如 `TPosition为A2/B2时，起始地址需512Byte对齐`）、硬件数据通路说明（如 `A1/B1对应L1 Buffer，A2/B2分别对应L0A Buffer/L0B Buffer`）
- 地址对齐按人工文档句式就近写入参数描述，例如：`LocalTensor的起始地址需要保证：TPosition为A1/B1时，32字节对齐；TPosition为B2时，512Byte对齐。`
- 禁止写法：`L0ABuffer`、`L0BBuffer`、`LocalTensor（L1 Buffer）`、`LocalTensor（L0A Buffer）`、`LocalTensor（L0B Buffer）`、`LocalTensor（L0C Buffer）`、`GlobalTensor（Global Memory）`、`L0A Buffer（A2）`、`L0B Buffer（B2）`、`L1 Buffer（A1/B1）`、`L0C Buffer（CO1）`、`Cube计算单元的本地存储（L0A Buffer/L0B Buffer）`

**描述**内容要点（按以下顺序组织）：
1. **功能和场景**：描述参数的使用场景和功能
2. **参数取值**：
   - 数值类参数：列出单位（数字和国际单位之间无空格，如"32字节"）、取值范围、默认值、支持的数据类型。单位和取值范围在原型中已明确且无特殊说明的可省略。范围写纯文本，如`取值范围：[1, 65535]。`，不要在表格单元格中使用LaTeX。不得把C/C++类型可表示范围当成接口合法范围；`2_extract.md`没有接口范围证据时保留`【待开发补齐】`
   - 数据结构类参数：列出结构体定义（过长时仅说明"结构体定义较长，以接口定义为准"），并详细介绍各成员。结构体成员说明必须使用简洁 Markdown 表格呈现，禁止使用 HTML 表格；如需表题，沿用参数说明表编号顺序，不得使用 `###` 子标题
   - 枚举类参数：若 `2_extract.md` 中给出了枚举定义，必须在参数描述中列出完整枚举定义，并单独说明当前接口支持的枚举取值；不得只写当前支持取值而省略枚举定义，也不得把完整枚举值集合表述为当前接口全部支持取值
   - 有特殊含义的取值不使用"魔鬼数字"，需解释取值含义
   - 对用于控制行为的参数或结构体成员，参数说明中首次出现控制功能名或缩写时必须就近解释其含义。禁止只写"标志/模式/控制参数，取值为..."或"是否启用/禁用 xxx 功能"这类悬空描述。对 `enable*`、`disable*`、`*Mode`、`*Flag`、`*Ctrl` 等控制参数，必须根据 `2_extract.md` 写清每个取值对应的行为差异、典型使用方式、与其他 API/参数的配合关系和不适用场景；若 `2_extract.md` 仍缺失具体语义，保留取值并标注"【待开发补齐】"；若证据冲突或需接口 owner 裁定，标注"【需开发确认】"，不得用泛化描述掩盖不确定性
   - 对 `2_extract.md` 标注为预留、内部使用或无需用户设置的参数/结构体成员，保留说明但不得写成普通可配置参数。统一写清用户操作要求，并优先采用人工文档句式：
     - 明确预留且有默认值：`该参数预留，传入默认值xxx即可。`
     - 暂未启用：`预留参数，暂未启用，为后续的功能扩展做保留，需要指定时，传入默认值xxx即可。`
     - 当前不支持：`预留参数，当前暂不支持。`
     - 不可配置：`预留参数，不可配置。`
     - 为后续功能保留且用户无需关注：`预留参数。为后续的功能做保留，开发者暂时无需关注，使用默认值即可。`
     - 自动推导/无需配置：`根据输入参数xxx自动推导，开发者无需配置该参数，保证xxx满足...即可。`
     - 内部使用：`该成员由接口内部使用，用户无需主动配置。`
   - 禁止只列出预留/内部/无需设置字段的默认值、取值范围或结构体定义，而不说明用户无需配置；若 `2_extract.md` 缺少可读取证据，保留参数并标注"【待开发补齐】"；若证据冲突或需接口 owner 裁定，标注"【需开发确认】"

## 约束说明

使用无序列表形式。以 `2_extract.md` 中"约束信息"章节为依据生成。约束说明应全面，保证资料内容完备性。
- 没有可输出的用户可见约束时，不生成列表或表格，`## 约束说明`章节正文只输出单独一行“无”，不得加句号、列表标记或附加说明。
- `## 约束说明` 下禁止新增 `###`、`####` 等子标题；约束类别、适用产品组和适用功能模式或重载必须写在无序列表项文字中。
- `## 约束说明` 中出现的所有表格必须使用简洁 Markdown 表格，禁止使用 HTML 表格

多参数组合约束写作规则：
- 凡 `2_extract.md` 中标注为"多参数组合约束"、"数据类型组合"、"参数组合合法性"或由 `SupportType<Tuple<...>>` 等证据提取的组合关系，必须写在 `## 约束说明`，不得放到 `## 参数说明` 下方
- 按产品组和实际函数原型展开。内部分析必须保留哪些参数共同参与组合约束；最终引导句使用已有模式名，无模式名时引用真实函数名，完整参与参数由紧随其后的组合表表头表达。
- 若 `2_extract.md` 确认联合约束还包含隐含语义操作数，约束表必须保留该维度，并使用用户可见角色命名列（如“初始结果操作数类型”），不得伪装为当前接口不存在的形参。只有闭环证据确认的数据类型/取值才能填写。
- `2_extract.md` 中每个适用原型组都必须在 `## 约束说明` 中有独立表述。参与约束的参数不同，即使组合值相似，也不得合并成少列的表或使用“同上”。
- 约束涉及 N 个参数，生成表格必须包含 N 个参数列；不得把 N 参数约束降维为 N-1 参数表，再用正文说明剩余参数的支持情况
- 约束列表项必须同时点明适用产品组和已有功能模式名；无模式名时引用真实函数名，并由紧随其后的表头表达实际参与参数。禁止用“包含某参数的重载”充当模式名称，也禁止写“参数集合为……”并枚举完整参数序列。
- 若某个重载在 `2_extract.md` 中只有支持/不支持信息、没有完整组合矩阵，生成阶段不得自行猜测组合；应保留 `【待开发补齐】` 并在 review 阶段判为需要补抽取；若已有证据互相冲突，才保留 `【需开发确认】`。

**数据类型/精度组合的表格组织：**
- 用**独立 Markdown 表格**呈现，与文档其它章节的表格风格保持一致，禁止使用 HTML 表格
- 表格直接跟在所属约束列表项的下方，**不写"表 N"编号标题**（表编号是参数说明章节专有，约束说明里的表不编号）。需要点明该表适用范围时，在所属列表项的文字里说明（如"以下产品支持的数据类型组合为："）
- **每个产品组单独成一张表**：当不同产品组的组合不一致时，分别成表；产品组在**所属列表项文字**中点明，禁止在表格内增加"支持产品"/"支持型号"列。组合完全相同的产品组才合并到同一张表
- **列顺序与列名**：每个参与组合的操作数各占一列，列名使用**实际参数名加 `type`**（参数名以函数原型为准），并按角色加中文前缀（如"源操作数""目的操作数"等）。列的排列顺序与组合约束在 `2_extract.md` 中的呈现顺序一致
- **列完整性**：表头必须覆盖 `2_extract.md` 中"适用参数集合"的全部参与约束参数。若参数集合为 `paramA/paramB/paramC/paramD`，表头必须包含 `paramA type`、`paramB type`、`paramC type`、`paramD type`；不得省略其中任一参数
- **备注列**：仅当 `2_extract.md` 明确标注了某些组合的附加适用条件/限定场景时，增加"备注"列写入该条件；`2_extract.md` 未标注则不加备注列，不得自行补写
- 表内各行数据类型按"数据类型写作顺序"排列；Markdown 表格不支持 `rowspan`，连续多行取值相同时必须在每行重复填写，不得留空
- 禁止使用"推断"、"标准组合"、"特殊类型组合"、"额外支持"、"还支持"、"支持与某原型相同组合"等概括或增量式表述；`2_extract.md` 未明确列出的组合不得自行补写

地址对齐要求写作规则：
- 若 `2_extract.md` 标注对齐要求来自`具体 API 约束`，按提取报告中的具体结论写入最终文档
- 若 `2_extract.md` 标注对齐要求来自`通用规则推导`，最终文档只写面向用户的技术结论，例如"srcTensor的起始地址需512Byte对齐"，不得输出推导过程、阶段证据说明、通用文档文件名或本地路径
- 若 `2_extract.md` 标注为`无法确认`、"【待开发补齐】"或"【需开发确认】"，保留该标记，不得自行套用通用对齐表补结论
- 具体 API 约束与通用规则推导同时出现时，以具体 API 约束为准

代码限定符写作规则：
- `__inout_pipe__(...)`、`#pragma begin_pipe(...)` 等编译限定符/管线标记只允许在函数原型代码块中原样出现
- 如果 `2_extract.md` 明确将此类标记作为用户可见约束，约束说明中只能原样写"接口原型包含 `__inout_pipe__(V)`"，不得解释为"Vector管线"、"Vector流水线"、"Vector Core管线"、"MTE管线"、"MTE流水线"等
- 如果此类标记不构成用户可配置或需遵守的约束，不在最终文档中额外说明

# 通用格式规范

## 调用示例

`## 调用示例` 是最终文档的最后一个章节。generate 阶段必须生成模型 fallback 示例；外部最终合成脚本若从 `0_call_example.md` 读取到脚本提取的有效示例，会替换本章节。若脚本未提取到示例，最终文档保留本章节。

### 生成规则

- 调用示例必须基于 `0_prototype.md` 和 `2_extract.md` 构造，参数个数、类型、顺序必须与函数原型一致。
- manifest 的 `memberApis` 多于一个时，每个成员至少出现一次真实函数调用。可共享资源初始化，但必须分别展示常规接口和同步接口的调用语句，并说明二者可观察差异；没有代码证据时只陈述调用完成，不编造同步机制。
- 必须标注 `【示例为基于函数原型构造】`。
- 示例代码只提供关键代码片段，不展开完整工程。
- 输入参数、关键接口调用需增加必要注释说明。
- 示例代码必须与功能说明匹配，禁止构造与 API 功能无关的调用。
- 核心调用路径中不得出现 `...`、伪地址、未声明变量或不可编译占位参数；必须包含变量声明、关键参数值、对齐/内存前提和目标 API 调用语句。
- `0_call_example.md` 未提取到真实样例时，必须从 `0_prototype.md`、`2_extract.md` 和 `0_cross_dir.md` 列出的实现代码中选择证据最完整、参数最少的重载，自行构造调用示例；禁止只输出 `【待开发补齐】缺少可验证调用示例。`。
- 模型构造示例必须包含资源声明、全部输入资源初始化、具体参数值和目标 API 调用。地址空间指针、Tensor、数组或缓冲区不得处于未初始化状态；无法直接构造底层数据布局时，应在代码注释和正文中写明调用前置条件，并使用已声明资源展示接口调用，不得使用省略号或伪地址。
- 每个示例都必须输出结果示例并使用 `text` 代码块。能由代码推导具体数值时给出具体输入输出；不能证明精确数值时，描述可证明的输出关系、元素范围、shape或存储位置，不得使用待补齐占位。
- 构造示例时，必须依据 `2_extract.md` 中的"输出参数初始化需求"判断输出参数是否需要调用前清零。只有代码明确读取输出参数旧值参与累加、原地更新、AtomicAdd 或注释明确要求预清零时，才按该要求初始化；实现覆盖写入时使用独立输出资源且不依赖旧值。优先选择参数值能够显式关闭累加、原地更新或其他不确定行为的重载。
- 构造示例中凡分配了 `LocalTensor`，包括 `sharedTmpBuffer`，必须配套释放或说明由框架管理。
