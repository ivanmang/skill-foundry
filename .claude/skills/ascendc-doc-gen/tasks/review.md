# AscendC 文档一致性校验任务

## 任务目标

对 `3_generate.md` 进行一致性校验和修正，**输出修正后的文档底稿**。
不是校验报告、不是 diff、不是对比表——是与 `3_generate.md` 结构相同但修正了不一致处的完整文档底稿。
以修正为主，保留原章节顺序、标题层级；`## 调用示例`缺失、只有占位或代码无效时，必须依据输入证据重构完整示例。
review 阶段不运行脚本、不写最终 `{API名}.md`；但必须保留并校验模型生成的 `## 调用示例`。最终文档由外部最终合成脚本生成；若脚本提取到有效调用示例，则替换模型生成的调用示例，否则保留模型生成的调用示例。

## 输入输出约定

### 输入

- `./outputs/{API名}/1_chipdiff.md` — 芯片差异分析报告（产品支持校验基准）
- `./outputs/{API名}/2_extract.md` — 信息提取报告（校验基准）
- `./outputs/{API名}/3_generate.md` — 待校验文档
- `./outputs/{API名}/0_prototype.md` — 外部预处理提取的函数原型（函数签名校验基准）
- `./outputs/{API名}/0_cross_dir.md` — 调用链与可读取实现文件清单（模型示例构造证据）
- `./outputs/{API名}/0_preprocess_manifest.json` — 文档 identity（规范文档名、成员闭集、调用约定和源文件范围）
- `./outputs/{API名}/0_semantic_links.json` — 跨公开包装接口参数传播候选，用于核对提取阶段是否形成闭环证据
- `references/common_terminology.yml` — 术语规范
- `references/chip_mapping.md` — 芯片→产品映射表
- `references/ascend_950_npu_architecture.md` — 昇腾950架构前置知识；技能启动时已读取，用于校验架构术语和表述边界，不作为新增事实来源

### 输出

- `./outputs/{API名}/4_review.md` — 修正后的文档底稿

**调用示例章节处理**：

1. `## 调用示例` 章节由 generate 阶段生成，作为脚本未提取到示例时的 fallback。
2. review 阶段必须校验并修正 `## 调用示例`，确保示例代码、参数顺序、结果示例和输出初始化行为符合本任务规则。
3. 外部预处理已将脚本结果写入 `0_call_example.md`；外部最终合成脚本只在 `0_call_example.md` 包含有效代码块时替换模型生成的调用示例。若脚本结果为 `【待开发补齐】` 等缺失提示，则保留 review 后的模型调用示例。

## 校验规则

**空章节格式（强制）**：逐项检查 `## 参数说明`、`## 返回值说明`、`## 约束说明`。内容为空时，章节正文必须精确为单独一行“无”，不得带句号、列表标记或附加说明；发现“无。”、“- 无”等形式时必须改为“无”。有实际内容时不得同时保留“无”。

### 规则 1：产品支持一致性

- 对照 `1_chipdiff.md` 中的逐产品支持结论，检查文档中的产品支持固定注释列表。
- 以下 7 组开始注释、结束注释、`npu` 值、`id`、产品名称和顺序必须逐字一致，每组都必须出现一次，不得省略、合并、增加或改写。
- 每行状态只能是“支持”或“不支持”，并与 chipdiff 结论一致；不得出现 `TODO`、`√`、`×`、`✓`、`✗`、斜杠或其它占位符。
- 产品支持章节禁止使用 HTML 表格、Markdown 表格和 `<term>` 标签。
- 若发现格式不一致，直接恢复为以下固定结构并填写正确状态：

```text
<!-- npu="950" id1 -->
- Ascend 950PR/Ascend 950DT：支持/不支持
<!-- end id1 -->
<!-- npu="A3" id2 -->
- Atlas A3训练系列产品/Atlas A3推理系列产品：支持/不支持
<!-- end id2 -->
<!-- npu="910b" id3 -->
- Atlas A2训练系列产品/Atlas A2推理系列产品：支持/不支持
<!-- end id3 -->
<!-- npu="310b" id4 -->
- Atlas 200I/500 A2推理产品：支持/不支持
<!-- end id4 -->
<!-- npu="310p" id5 -->
- Atlas推理系列产品AI Core：支持/不支持
<!-- end id5 -->
<!-- npu="310p" id6 -->
- Atlas推理系列产品Vector Core：支持/不支持
<!-- end id6 -->
<!-- npu="910" id7 -->
- Atlas训练系列产品：支持/不支持
<!-- end id7 -->
```

模板中的 `支持/不支持` 只表示二选一，修正后的正文必须替换为单一状态。

### 规则 2：函数原型一致性

- 文档中的函数原型必须优先与 `0_prototype.md` 中提取的原型完全一致；`2_extract.md` 用于校验原型语义、适用产品和参数说明
- **【强制检查】文档成员与调用约定隔离**：读取 manifest 的 `documentApiName`、`memberApis` 和 `callingConvention`。`## 函数原型` 必须覆盖全部成员及其全部重载，且只能包含成员闭集中的函数名和指定调用约定；漏掉常规/同步成员、混入 `_s4`/`_sparse`/`_mx` 或其它调用约定均须修正。
- **【强制检查】逐成员分组**：`memberApis` 多于一个时，使用普通列表项按真实函数名分组；每个函数名下只允许使用 `2_extract.md` 已确认且有代码证据的功能模式名称。`## 函数原型` 下禁止出现子标题，不同函数名不得放入同一 C++ 代码块。
- 检查项：函数名、参数名、参数类型、模板参数、返回值类型、限定符
- 禁止遗漏任何原型变体
- 多原型时，区分说明只能使用 `2_extract.md` 中“功能模式名称 -> 对应原型 -> 代码证据”的闭环结论。参数名、参数集合和原型序号不能充当功能模式名称。
- **【强制检查】禁止自造版本名**：全文不得出现“精细控制版本”“简化计数版本”“Count版本”“同步版本”“标准版本”“特殊版本”等代码中不存在的分类名。发现后优先恢复为 `2_extract.md` 已确认的用户可见功能模式名称；无证据时直接删除分类说明，只保留真实函数名。
- **【强制检查】原型逐项一致**：以`0_prototype.md`为签名唯一基准，逐个比较函数名、限定符、返回类型、模板参数、参数类型和参数名；`## 函数原型`中的原型数量及签名集合必须与`0_prototype.md`完全一致，不可多、不可少、不可改写
- **【强制检查】禁止代表性压缩**：出现“以T为例”“其余类型相同”“同样包含”等替代原型的表述时，必须从 `0_prototype.md` 恢复所有缺失签名。允许同组多个声明共用一个代码块，但不能省略任何声明
- **【强制检查】原型分组格式**：优先使用 `2_extract.md` 已确认的功能模式或产品组；无模式名时列表标签只写真实函数名，并在同一代码块完整列出该函数的全部重载。发现“包含某参数的重载”“原型1”“参数集合”等机械分组时必须删除。
- **【强制检查】不同签名组织**：同一真实函数名的全部重载可以放入同一 C++ 代码块。只有 `2_extract.md` 已确认不同用户可见功能模式时才按模式拆组；不得因参数名序列不同而创建机械分组名称。
- **【强制检查】原型格式**：函数原型必须使用 C++ 代码块；每个函数声明独占一个物理行并保留末尾分号，模板声明行单独保留。发现手工折行、漏分号或与 `0_prototype.md` 文本不一致时必须恢复。

### 规则 3：参数说明完整性

- 所有函数原型中的参数必须在参数说明表中出现，不可遗漏
- 参数名必须与函数原型中的一致
- 输入/输出方向必须正确
- 数据类型排列顺序必须按位宽从小到大
- **【强制检查】参数完备性**：逐一核对函数原型中的模板参数和接口参数，确保每个参数在参数说明表中都有对应行；发现遗漏必须从 `2_extract.md` 补全
- **【强制检查】参数名一致性**：参数说明表中的参数名必须与函数原型中的参数名**逐字一致**，包括大小写和下划线
- **【强制检查】正式形参闭集**：参数表不得新增 `0_prototype.md` 中不存在的参数。关联公开接口参数和隐含语义操作数只能作为正式参数的语义/约束说明，不能伪造成当前接口参数行。
- **【强制检查】隐含语义操作数闭环**：逐项核对 `2_extract.md` 的“公开参数与隐含语义操作数映射”。已由声明、调用链、同落点公开参数及实现/校验/ISA证据闭环确认的语义、适用条件和数据类型不得遗漏；只有 `mapping_only` 或 `name_hint_only` 候选而未闭环的内容必须删除或保留待补齐，不得写成确定事实。
- **【强制检查】隐含约束维度**：联合数据类型或参数组合包含隐含语义操作数时，约束表必须保留其用户可见角色维度，但列名不得伪装为不存在的正式参数。
- **【强制检查】枚举定义完整性**：若 `2_extract.md` 中某个参数包含 `enum`/`enum class` 完整定义，参数说明表对应描述必须包含该完整枚举定义，并在参数表后使用独立 C++ fenced 代码块呈现；不得把多行代码放入 Markdown 表格单元格，也不得仅保留当前接口支持取值。完整枚举定义与当前接口支持取值必须分开表述，当前接口支持取值仍需与 `2_extract.md` 中的约束结论一致
- **【强制检查】无注释参数保留**：不得因为头文件缺少 `\param` 注释而删除或弱化函数签名中的参数。`blockCount`、`blockLen`、`srcGap`、`dstGap`、`srcStride`、`dstStride`、`repeatTimes`、`mask` 等控制参数必须逐项出现在参数说明表中，并说明其单位、范围、"【待开发补齐】"或"【需开发确认】"
- **【强制检查】控制参数语义完整性**：用于控制行为的参数或结构体成员不得只写"标志/模式/控制参数，取值为..."，也不得直译代码注释中的泛化描述。必须逐项说明取值行为、使用方式、配合关系和限制；若 `2_extract.md` 没有提取到具体语义，缺少可读取证据时标注"【待开发补齐】"，证据冲突或需接口 owner 裁定时标注"【需开发确认】"
- **【强制检查】弱证据不得包装成语义**：若 `2_extract.md` 只确认参数透传、下游实参位置、同族名称或测试哨兵值，删除由参数名直译出的“某某模式选择/控制参数”式完整结论。可确认所属公开功能时，只保留有限功能说明，并把支持取值、编码位宽和逐值行为分别标注为待补齐；不能确认所属功能时直接保留待补齐项
- **【强制检查】证据过程话术清理**：最终文档不得出现“无法从公开代码确认”“实现仅透传”“代码未给出”“未发现校验”“现有证据不足”等面向生成过程的措辞。改为直接指出缺失内容，例如“取值范围【待开发补齐】。”或“各取值对应的行为【待开发补齐】。”
- **【强制检查】用户配置要求**：若 `2_extract.md` 标注某个参数或结构体成员为预留、内部使用或无需用户设置，最终文档必须保留该状态说明，并写明用户动作：传默认值、不可配置、暂不支持、无需配置或保持默认值。不得把预留位、填充字段、内部编码字段、仅由实现内部赋值的字段、或用户传入但底层未实际使用的参数写成普通可配置参数；若缺少可读取证据，必须保留"【待开发补齐】"；若证据冲突或需接口 owner 裁定，必须保留"【需开发确认】"
- **【强制检查】预留参数证据边界**：若 `2_extract.md` 未给出预留、内部使用、无需配置或底层未使用的调用链证据，review 阶段不得自行把参数改成预留参数。若最终文档把实际参与计算、分支、校验、地址/shape/临时空间计算、数据类型组合判断、输出布局或底层 intrinsic 实参的参数写成预留，必须改回普通可配置参数，并保留 `2_extract.md` 中的真实行为说明
- **【强制检查】预留参数句式归一**：若文档只写"预留参数"、"保留参数"或只列默认值，必须根据 `2_extract.md` 结论补成明确用户动作。优先使用人工文档句式：`该参数预留，传入默认值xxx即可。`、`预留参数，当前暂不支持。`、`预留参数，不可配置。`、`开发者无需配置该参数，保证xxx满足...即可。`
- **【强制检查】参数说明格式**：默认使用规范表题加 Markdown 表格。只有 `2_extract.md` 明确确认不同功能模式或重载中同名参数语义、单位、范围或约束不同，才允许使用 `### {功能模式}参数` 子标题并分别建表；模式名称必须有证据，无模式名时不得创造分类标题。
- **【强制检查】表格单元格格式**：Markdown 表格单元格内禁止出现 `$...$`、`\le`、`\ge`、转义下划线等 LaTeX 表达；取值范围必须改为纯文本，如“取值范围：[1, 65535]。”
- **【强制检查】Markdown 表格内联格式**：参数名、类型和字面量使用 `<code>...</code>`；禁止在单元格内放置 fenced 代码块或多行原始 HTML
- **【强制检查】表格分段**：同一描述单元格中的含义、单位、范围、产品限制、特殊说明、待补齐项必须使用 `<br>` 分行。发现多个语义挤在同一行时，必须拆分
- **【强制检查】普通控制参数最小表述**：`repeat`、`count`、`size`、`stride`、`gap`、`len_burst`、`n_burst` 等参数若 `2_extract.md` 只给出简单语义，不得扩写内部机制或绑定自造版本名；例如 `repeat` 应修正为`迭代次数。`

### 规则 3.1：流水类型与公式有效性

- `## 流水类型` 是可选章节。只有 `2_extract.md` 提供显式公开流水类型、编译管线标记或完整 ISA 映射证据时才保留；由底层 intrinsic 名称或目录推断出的流水类型必须删除
- 未输出该章节不构成缺失；证据不足时不得写“PIPE_MTE2”等猜测值

### 规则 3.2：公式有效性

- 计算公式不是必选项。只有 `2_extract.md` 明确给出可确认公式，且该公式不是由底层 intrinsic/helper 调用改写而来时，最终文档才保留公式
- **【强制检查】伪公式删除**：发现公式中出现底层 CCE intrinsic、helper、实现函数或调用路径，例如 `vreducev2`、`vcopy`、`set_mask_count`、`asc_set_mask_count_begin`、`*Impl`、`*Cal`，必须删除公式块，改为保留功能行为描述；不得把内部调用当成数学公式
- **【强制检查】公式符号闭包**：公式中出现的每一个符号都必须在公式后的说明中解释，包括函数参数、模板参数、结构体字段、辅助变量和下标变量。发现未解释的 `i`、`j`、`k`、`n`、`m`、`r`、`c` 等符号时，必须从 `2_extract.md` 补全说明；若 `2_extract.md` 缺失，删除公式并保留 `【待开发补齐】`
- **【强制检查】索引范围**：公式中出现下标或循环索引时，必须说明索引语义和取值范围。例如块搬运/广播类公式中，`i` 为块索引，取值范围应与 `blockCount` 对应；`j` 为块内索引，取值范围应与 `blockLen` 对应
- **【强制检查】控制参数不强行入公式**：函数原型中影响计算范围、地址偏移、步长、重复次数、mask、axis、shape、block/gap/stride 的参数若无法从 `2_extract.md` 确认其数学作用，不得为了覆盖参数而补写公式；应在参数说明或约束说明中描述其用户可见作用

### 规则 4：数据类型一致性

- 参数说明中列出的数据类型必须与 `2_extract.md` 中提取的 `\note support data type` 一致
- 不同 API 支持的数据类型可能不同，不可混用
- 数据类型写作顺序必须按固定顺序
- **【强制检查】逐原型数据类型**：若不同函数原型支持的数据类型不同，必须分别标注，禁止用并集覆盖
- **【强制检查】产品差异数据类型完整列出**：若不同产品支持的数据类型不同，参数说明表中必须按产品组完整列出每组支持的数据类型。禁止使用"额外支持"、"还支持"、"除xxx外支持"等增量式描述；发现这类描述时，必须改为每个产品组的完整支持集合。例如将"产品A支持float；产品B额外支持int32_t"改为"产品A，支持的数据类型为：float。产品B，支持的数据类型为：float、int32_t。"
- **【强制检查】避免全局行与分组行混用**：若已按产品组列出数据类型，不得再保留"支持的数据类型为：..."的全局数据类型行，除非所有产品数据类型完全一致
- **【强制检查】多参数类型组合位置**：若数据类型约束是由多个参数共同组成的合法组合，不得只写在某个单参数描述中，也不得放在参数说明表后作为参数说明补充；必须作为跨参数组合约束放入 `## 约束说明`
- **【强制检查】实际原型覆盖**：逐项比对 `2_extract.md` 的实际原型清单和多参数组合约束。每个存在联合约束的原型组必须保留独立约束表述；引导句使用已有模式名，无模式名时引用真实函数名，完整参与参数由表头表达。
- **【强制检查】组合维度不得降维**：若 `2_extract.md` 记录的组合涉及 N 个参数，最终文档表头必须包含这 N 个参数列。出现 N-1 列表格再用"另一个参数也支持/存在/不传入/传入"等文字补充的，判为错误，必须退回补全完整 N 列组合
- **【强制检查】组合关系不得概括**：不得使用“标准组合”“特殊类型组合”“同上”或“与某原型相同”替代完整组合。必须按产品组和实际函数原型列出组合表，表头使用全部实际参与参数名；表前引导句不得写“参数集合为……”并枚举参数。

### 规则 5：约束信息一致性

- 功能说明中的使用约束必须完整反映 `2_extract.md` 中提取的所有约束
- 约束说明章节不可与功能说明中的使用约束矛盾
