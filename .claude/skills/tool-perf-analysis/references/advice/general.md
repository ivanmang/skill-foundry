# 通用类条目正文（§1.1–§1.8）

> 由 [optimization-advice.md](../optimization-advice.md) 索引按触发条件命中后读取；五槽位格式与收益纪律见该文件 §0。

## 1.1 流水未重叠 → 双缓冲

- **证据**：PipeTrace 时间轴上 MTE2 时间片集中在前段、VECTOR 集中在后段，两者无交替；或 `mte2_ratio + vec_ratio ≈ 1`（互不重叠地分掉全部时间）且单侧利用率均不高
- **方向**：UB buffer 单缓冲改双缓冲，第 n+1 块搬入与第 n 块计算并行。主循环改 prologue 预取 / hot loop / epilogue 三段结构，MTE2 与 VECTOR 之间用事件同步（生产者-消费者）而非全局 barrier
- **收益**：MTE2/VECTOR 重叠度 0% → 80–90%，吞吐提升 20–50%
- **代价与前置检查**：UB 占用翻倍（`tile_size × tensor 数 → 2 ×`）。超 UB 预算时先缩小 tile_size 再开双缓冲，联合调参；tile 数 < 3 时收益被 prologue/epilogue 摊薄
- **排除条件**：`mte2_ratio ≈ 0.0001`（搬运已完全隐藏，无可重叠余量）；时间轴已见 MTE2/VECTOR 交替（双缓冲已生效）
- **如何验证见效**：重采后时间轴是否交替，`mte2_ratio + vec_ratio` 是否显著 > 1——重叠成立的直接标志

## 1.2 小 Shape 核启动开销主导 → 核数裁剪

- **证据**：各计算单元利用率均不高 + 带宽利用率低 + `aicore_parallel_utilization` 偏低，且元素总量小；核在等而不在算
- **方向**：不用满核。按 `min(满核, ceil(A1 / min_rows_per_core))` 收缩核数，每核设最小任务行数下界，使单核计算量足以掩盖启动开销。与"多用核"相反，是小 Shape 下的常见反直觉点
- **收益**：需实测；含 SyncAll / 跨核归约的算子收益更大（同步次数随核数线性下降）
- **代价与前置检查**：需要 `A1`（并行切分维度总任务量）与满核数，`A1` 报告不可见 → 须用户提供 tiling data。裁核后单核耗时上升，总耗时下降才算有效
- **排除条件**：Cube 类（matmul 等）核数由 L1 切分决定，不走裁核路径；`A1 / core_num` 已足够大（计算占主导）；多核归并类（sort）须与归并轮数 `ceil(log(core_num))` 联合评估，裁核可能反噬
- **如何验证见效**：重采看总耗时（非单核耗时）下降、`aicore_parallel_utilization` 上升

## 1.3 block 间负载不均 / tail block → 尾块处理

- **证据**：逐 block 离散度 `max/min > 1.10`，或末块耗时远低于 median 的 tail block；`aicore_parallel_balance` 偏低
- **方向**：双轨制切分——Host 侧把核分为正常核（处理 `defaultUbFactor` 整数倍）与尾核（单独算尾块循环次数与尾块大小），Kernel 按 `blockIdx` 选参数；尾块用向量化掩码处理替代标量循环；非对齐边界用带 padding 的搬运而非截断
- **收益**：尾块向量化处理提升 4–8 倍（单次处理 64 元素）；非整除场景整体提升 10–30%
- **代价与前置检查**：正常核/尾核两套循环参数，代码分支增加；确认非对齐访问是否已按 32B/64B 对齐
- **排除条件**：离散度 < 1.10 且无 tail block（已均衡，改造无收益）；tail block 绝对耗时占比极小（总耗时不受制）
- **如何验证见效**：重采看离散度回落 1.10 以内、`aicore_parallel_balance` > 0.9

## 1.4 冗余 GM 搬运 → UB/TBuf 常驻复用（附 bank 冲突规避）

- **证据**：`mte2_ratio` 偏高但带宽利用率不高（搬运忙而不满，指向"次数多"而非"量大"）；或同一小块参数在多 tile/loop 中被反复读入
- **方向**：小尺寸参数（weight / gamma / scale）与跨迭代状态（累加器、递推结果）常驻 UB/TBuf——循环外一次搬入，循环内片上读写；临时 buffer 由"各阶段求和"改为"并发峰值取最大"分时复用
- **收益**：参数搬运次数降 N 倍（N = tile/loop 数）；临时 buffer 总量降 30–60%
- **代价与前置检查**：管理常驻 buffer 生命周期与分区 offset；常驻挤占 UB，与 §1.1 双缓冲争同一预算，须联合核算
- **附带风险（必须一起查）**：地址分配不当引入 UB bank 冲突，Vector 单 Repeat 从 1–2 拍退化到多拍。bank 结构随架构不同（DAV_2201：192 KB / 48 bank / 16 group / 3 bank per group；DAV_3510：256 KB / 16 bank / 8 group / 2 bank per group；同 group 的 bank 满足 `bank_id % group 数` 相同），改造后按报告中的架构型号核对
- **排除条件**：`mte2_ratio ≈ 0`（搬运已隐藏）；无跨迭代复用的小参数（纯流式逐元素算子）
- **如何验证见效**：重采看 `mte2` 搬运次数与 `datas(KB)` 总量下降；确认 `vec_ratio` 未因 bank 冲突恶化

## 1.5 搬运效率低（对齐/粒度/离散）→ DataCopy 优化

- **证据**：带宽利用率低但 `mte2/mte3_ratio` 不低；或 `mte2_wait_ratio > 0` 而资源冲突为 0（供给侧效率问题）；存在大量小于最优粒度的搬运
- **方向**：五方向按适用性挑选——① 非对齐数据带 padding 搬运自动对齐；② ND→NZ 格式转换融合进搬运，省掉独立转换算子的一次 L1 往返；③ 非连续列用 `blockLen + srcStride` 一次提取，替代"搬全量再裁剪"；④ 循环内小搬运累积到 UB、循环外一次写回，压缩 DMA 启动次数；⑤ 离散访问用向量化 gather/scatter 替代逐元素读写
- **收益**：按设备最优粒度对齐带宽最高提升 30%（32B 对齐仅为 512B 对齐的约 70%，最优粒度按设备实测）；DMA 启动 `loopCount` 次 → 1 次；离散访问向量化提升 5–20 倍
- **代价与前置检查**：对齐引入 padding 冗余字节，须确认冗余量小于对齐收益；最优对齐粒度是设备参数（如某架构 512B），报告不可见 → 查硬件手册或实测
- **排除条件**：带宽利用率已 > 80%（搬运已高效）；搬运总量本身极小
- **如何验证见效**：重采看 `bw_usage_rate` 上升、`mte2/mte3` 段耗时下降；分子分母口径（单块 vs Σ 块）保持一致，否则结论作废

## 1.6 Vector 主导但指令效率有空间 → Vector 计算效率优化

- **证据**：`vec_ratio` 高（尤其 ≥ 65%）且 `scalar_ratio` 非零；或 `sfu_ratio` 明显（特殊函数参与）；或多步 Vector 链之间落地 GM 的痕迹（`mte2/mte3` 次数与计算步数同量级）
- **方向**：三处入手——① Counter 模式一次设置覆盖全部数据，免去每条 Vector API 前的 repeat/mask 手算，削减 Scalar 控制指令；② 多步 Vector 链中间结果留在 UB 内链式消费不落 GM，搬运次数 `2n` → 2；③ 归约路径用低延迟指令组合替代单条高延迟归约；循环展开暴露指令级并行
- **收益**：Scalar 开销降 30–50%；n 步链搬运次数降 n 倍；归约延迟降 20–40%
- **代价与前置检查**：UB 内融合链需额外中间 buffer，与 §1.1 / §1.4 争 UB 预算；`vec` 时间的指令构成（Cast / 超越函数占比）报告不可见 → 需指令级 trace 才能定位到具体哪一步
- **排除条件**：`vec_ratio > 80%` 且指令级已确认超越函数主导——VEC 已近理论极限，单算子层面空间有限，转向算法或融合层面；`scalar_ratio` 与 `mte` 次数均已很低
- **如何验证见效**：重采看 `scalar_ratio` 与 `mte2/mte3` 搬运次数下降，`vec_vf_ratio` 相对 `vec_ratio` 的比值上升（指令有效性提升）

## 1.7 scalar 占比过高 → Scalar 编码原则排查

- **证据**：`scalar_ratio > 0.1`（典型 ScalarBound）；或 `icache_miss_rate > 0.01` 伴随高 scalar
- **方向**：ScalarBound 主因通常**不是标量计算指令多，而是 Load/Store 多**（典型占比超 30%），根源是编译器寄存器 spill。所有改法的共同目标是帮编译器做好寄存器分配、别名分析与常量传播。九条原则：① 结构体内慎用数组（动态下标让编译器放弃整个结构体的常量传播）；② 循环拆 prologue / 零分支 hot loop / epilogue 三段；③ 显式写嵌套 for 替代隐式状态机（for 回跳走专用硬件，不进分支预测）；④ 优先局部变量（成员变量受别名分析压制，跨函数调用后必须重新 Load）；⑤ 变量定义贴近使用点（缩短活跃范围即降低 spill 概率）；⑥ 避免多级指针解引用（每级都是带依赖的 Load）；⑦ 避免超大结构体（> 64B 跨 cacheline，超寄存器容量必 spill）；⑧ 编译期常量用 `constexpr` / 模板参数承载（`const` 成员对编译器仍是 runtime Load）；⑨ hot loop 内不构造对象、不取地址（构造展开为大量初始化 Store；取地址迫使编译器假设变量可被外部修改而强制 spill）
- **收益**：需实测；Load/Store 占比是直接观测量，下降幅度即收益
- **代价与前置检查**：纯编码层改动，不动算法与 tiling，风险低；需指令级统计确认 Load/Store 占比，报告不可见 → 列入数据缺口
- **排除条件**：`scalar_ratio < 0.1`（标量不构成瓶颈，九条原则改了也不快）
- **顺序说明**：Scalar 优化与算子族优化**正交**——族优化决定"做什么计算和搬运"，Scalar 优化决定"指令能否被及时分发"。两者都要做，但**族优化（tiling / MTE 策略）在先**
- **如何验证见效**：重采看 `scalar_ratio` 下降、其他 pipe 的 bubble 收敛

## 1.8 SIMT 模式确认 → 手段切换（避免套错经验）

- **证据**：`simt_vf_ratio == vec_ratio` 且 `vf_ratio == 0` → 算子走 SIMT 模式（C2 类核）
- **方向**：SIMT 优化手段与常规 VF 模式不同，先切换思路再动手：① VF 函数内避免 if / else / switch——分支导致线程分化，同 warp 内部分线程等待另一部分，产生流水气泡；条件可编译期确定时用模板参数把分支提到编译期彻底消除；② 关注 memory coalescing 与向量化读写——逐元素读写的带宽利用率可低至 6.25%，应让每线程处理连续多元素
- **收益**：向量化读写在逐元素基线上收益可达一个量级（6.25% 带宽利用率是可量化的改进起点）；分支消除需实测
- **代价与前置检查**：模板参数化产生代码膨胀（每个分支组合一份实例）；确认分支条件确实可在编译期或模板层确定
- **排除条件**：`vf_ratio > 0`（非 SIMT 模式，本条不适用，改走 §1.6）
- **如何验证见效**：重采看带宽利用率与 `simt_vf_ratio` 的比值变化；分支消除看 `vec` 段 bubble 减少
